# 05 开发

目标：按已审核的模块计划把代码写出来，并且**由实际运行来证明它能用**。条件不具备就停，不猜；**每个界面都照着设计依据（Figma 节点或设计稿 / 设计图）做，没有设计依据的界面不做**。

```
开发计划审核通过
→ 打样（符合条件时）：走通主链路，Codex 实际运行，用户确认方向
→ Claude 按模块写代码：后端 → 前端；每个模块写完自己审核，最多 3 轮，问题记下来
→ 全部模块写完（并行开发的先汇总）
→ Codex 检验：先冒烟，再核实 Claude 记下的问题，再跑测试和验收路径
→ 反馈给 Claude 修 → Codex 复检
→ 统一联调（M99）→ 用户验收
```

| 谁 | 做什么 |
|---|---|
| Claude | 写计划；后端、前端的代码都写；每个模块自己审核；写给 Codex 的检验计划；按 Codex 的反馈修 |
| ChatGPT / Codex | 实际运行：编译、跑测试、连本机后端走验收路径、截图；核实 Claude 记下的问题；只修检验计划允许的小问题 |
| 用户 | 审核计划；看打样结果定方向；处理问题清单里要拍板的事；统一联调和验收 |

## 1. 开始前（每次新会话都要做）

1. **读代码仓库根目录的 `AGENTS.md`**（Codex、Cursor 会自动加载；Claude Code 通过 `CLAUDE.md` 导入）。里面写着项目工作区的路径。
2. 读工作区 `README.md` 找到开发中版本，读该版本 `04-开发计划/开发计划.md`（总计划），**只看模块清单表和并行安排**，确认这次要做哪些模块、在哪个分支和目录。
3. **一次只读正在做的那一个模块计划** `04-开发计划/模块/Mxx-*.md`；做完一个模块再读下一个。不通读 `05-测试/` 的历史记录。线上问题读 `修复单.md`。
4. 确认模块状态是"已审核"或"执行中"。**不是的话不写业务代码**，只可以读代码、回答问题、帮忙写计划。
5. 按 `AGENTS.md` 的「规范索引」读本模块相关的规范；换到另一个仓库做下一组任务之前，先读那个仓库的 `AGENTS.md`。
6. **复核开工条件**（第 2 节），设计核对第一个做。**核对完、没有缺失之前，不写前端代码。** 后端任务不涉及界面，可以先做。
7. **建任务列表**（第 12 节），让用户在对话旁边看得到进度。

> 工作台里的 `templates/repo-rules/` 只是新项目的模板。编码时以**代码仓库里的规范**为准。

## 2. 开工条件复核

对着模块计划 §1 逐项**实际检查**，不是读一遍计划里写的"已满足"：

- **设计（最先做）**：
  1. 实际打开 §4 每一行的设计依据：Figma 节点用 Figma 工具读取，设计图文件实际打开查看。读不到、打不开就算缺。
  2. 对照本模块的 AC 和 §8 验收路径，找出用户会看到、但 §4 没有列的界面或状态（弹框、提示、空状态、错误状态等）。
  3. 把缺失、打不开、和计划描述对不上的**全部汇总，一次性报告给用户**，写成「设计缺失清单」：缺哪个界面 / 状态、对应哪条 AC、影响哪些任务、建议。
  4. 清单为空才能开始做前端任务。
- **外部条件**：执行计划里写的验证方法（例如请求一次测试接口），确认账号、Key、环境可用。
- **前置模块**：依赖的模块代码已写完、自审已做。依赖的模块是“阻塞”时，本模块也标“阻塞”并跳过。
- **测试基线**：模块计划写了基线结果。没有记录的，先记（自己跑不了就写进给 Codex 的计划），不要带着不清楚的基线开工。

任何一项不满足：

1. 在模块计划 §1 把该项改为"阻塞"，写清缺什么、需要谁提供。
2. 总计划里本模块状态改"阻塞"，“等谁”写上要谁处理。
3. 不写该模块受影响部分的代码（缺设计时是前端任务），计划没写明的别猜。只执行这一个模块时：向用户报告并停下。连续执行多个模块时：写进报告，继续做不依赖它的下一个模块。

## 3. 打样

总计划写了要打样（`04` 第 2 节）的版本，**打样通过之前不写任何模块**。

1. 只做总计划写的那一条最窄的主链路：从界面点一下，经过接口、数据库、外部服务，结果回到界面。不做界面细节、异常处理和其余功能。
2. Claude 写完后，写一份给 Codex 的检验计划（`04` 第 12 节），只有一件事：在本机把这条链路实际跑通，留下截图或日志。
3. 把结果给用户看：链路通没通，总计划里“要证明的那几件事”各自的结论，路线有没有偏。
4. **用户确认后才开始写模块。** 没通过：回去改技术方案或计划，不靠多写代码来绕过去。
5. 打样的代码留下来当骨架，后面的模块在它上面接着写。

## 4. 界面开发规则

- **每个界面都必须照着 §4 的设计依据做**（Figma 节点或设计稿 / 设计图），开发时打开对照，不凭记忆、不凭描述。
- §4 里没有的界面、状态、弹框、提示、组件、图标：**一律不做**，包括"临时的""占位的""先做个简单版"。不"参考类似页面"，不自己设计，不用近似图替代。
- 缺失应该在开工前的设计核对（第 2 节）里全部发现。**开发中途仍发现缺界面，说明核对漏了：这个模块的前端停下**（模块状态改"阻塞"），报告缺哪个界面或状态、对应哪条 AC、影响哪些任务、建议（补稿，或沿用哪个现有页面）。不能自己先做一个等用户改。
- 用户补稿，或明确回复"沿用某页面"后，由写计划的人写进 §4（含原话和设计图），再继续。
- 图标、插图从对应 Figma 节点或设计切图导出 1x / 2x / 3x，不得自己画或拼接。
- 业务动态内容（文案、数据）和设计示例不同时，以业务为准，在"结果"里写一句不同之处；布局、间距、颜色、字号按设计稿。
- 和设计图同视口并排截图的核对，由 Codex 在检验时在真实运行的 App 里做（第 9 节）。

## 5. Claude 写代码：每个任务的循环

一个模块先做完全部后端任务，再做前端任务。

1. 把任务状态改为"进行中"。
2. 按"具体做法"实现。**只改"仓库与文件"里列出的文件。** 要动其他文件，尤其是另一端的、别的模块的文件：先说明改哪个文件、为什么，再改，并记进任务"结果"；涉及接口、约束、模块外 Service 的，同时补进接口改动总览。**不许不说就改。**
3. 前端直接连本机后端，**不做假数据**。
4. 验证：任务里写的命令，自己的环境能运行的就运行。**运行不了的在"结果"里写"没运行：××"，不能写成通过，也不能用"应该没问题"代替。** 后端只测本任务改到的模块：只跑任务里写的 `./gradlew test --tests '…'`，确认编译用 `./gradlew compileJava compileTestJava`；不跑不带 `--tests` 的 `./gradlew test`，也不跑 `./gradlew build`。全量测试只在统一联调（M99）做一次。
5. 任务状态改为"完成"，"结果"最多 5 行：做了什么、提交号、哪些验证没运行、证据路径。
6. **每个端做完单独提交一次**，不推送。提交信息带版本号、模块号、任务号，例如 `v2.2.0 M02 B-03: 订单保存商店实际币种`。

## 6. 模块写完后自己审核（最多 3 轮）

一个模块的后端、前端任务都“完成”后做。每一轮对着下面固定的四样逐项查，不是泛泛地再看一遍：

1. **改动和接口改动总览对不对得上**：自己看 git diff，列出实际改的接口、请求和返回对象、迁移脚本、模块之间公开的方法、模块外的 Service，和总览逐行对比。
2. **每条 AC 做到没有**：对着模块计划 §5 的 AC 对照表，一条一条指出是哪段代码实现的。
3. **有没有计划外的行为变化**：接口没变但结果、限制、默认值、流程推进方式变了的。有就按第 7 节处理，不能只记在“结果”里。
4. **有没有改计划没列的文件**；有没有 §4 之外的界面、状态、组件；有没有“顺手”的改动。

每一轮：查出问题 → 改 → 再查。记录写在模块计划 §11：第几轮、查出了什么、改了没有。

- 3 轮后还没解决的，以及拿不准的（例如“这段逻辑不运行看不出对不对”），登记到总计划的问题清单，类型写“自审遗留”，写清希望 Codex 怎么验证。
- 自审做完：总计划里本模块“自审”写“通过”或“有遗留”，状态改“待检验”，“等谁”写 Codex。**不停下来等用户，继续做下一个模块。**

## 7. 遇到计划外情况

**立即停下来问用户**的只有三种：

- 需要新增或改变接口改动总览以外的接口、接口约束、表结构或流程推进方式；
- 涉及钱、权限、删除数据，而计划没有写；
- 计划写的文件或仓库不存在，整份计划无法执行。

其他情况**记下来，继续做**：把这个模块（或受影响的任务）标“阻塞”，原因登记到问题清单并选好类型，做不依赖它的下一个模块，最后一起报告。包括：

- 设计稿缺失或和计划不一致；产品规则不明确、AC 之间矛盾、需求没有定义的行为（类型“需求没写到”）；
- 计划漏了某件事、计划写的做法行不通（类型“计划漏写”）；
- 决定不做计划里的某一项（类型“没做”，写原因，不能悄悄跳过）；
- 外部条件失效（Key、环境、渠道）。

**不得在对话里或计划里直接改产品规则。** 用户决定后，由写计划的人先改 `requirements.md`（涉及设计、技术的一并改），再改计划（`04` 第 10 节），然后继续。

## 8. 并行开发和汇总

| 规定 | 说明 |
|---|---|
| 一个并行任务一个分支、一个目录 | 并行的任务各开一个 git 工作区（`git worktree add <目录> -b <分支>`）。两个对话不在同一个目录里同时改代码 |
| 顺带的小修改不用另开工作区 | 直接在当前分支改。改之前说明改哪个文件、为什么，单独提交 |
| 只有计划写了能并行的才并行 | 看总计划的并行安排。模块“会改的文件和目录”有重叠的，按顺序做 |
| 公共文件按总计划分好的来 | 迁移脚本版本号、多语言 key、路由表、`api.md` 的小节。并行期间不改接口 |
| 各管各的文档 | 每个对话只改自己那份模块计划；总计划只由主对话改。其他对话要更新总计划里自己那一行时，告诉用户或主对话 |
| 同时进行的任务有上限 | 同一个代码仓库最多 3 个（暂定） |
| 汇总是单独一步 | 并行的模块都写完、自审做完后，由主对话按总计划的顺序合并分支、解决冲突、确认能编译，再写给 Codex 的检验计划。合并时改了哪些冲突，写进总计划的调整记录 |

## 9. Codex 检验

全部模块写完（并行的已汇总）后做，一份检验计划覆盖全部模块。计划由 Claude 照模板写，放 `04-开发计划/待执行/`，文档和仓库都写绝对路径（`04` 第 7、12 节）。按这个顺序：

1. **冒烟**：编译、启动、把主链路走通一遍。不通就停，把现象和日志反馈回来，不往下做。
2. **核实问题清单**：Claude 记下的每一条，给结论——属实 / 不属实 / 没法验证，附证据（日志、截图、接口返回）。
3. **测试**：和测试基线对比。新增的失败才算这次的问题；基线里本来就失败的，标“既有问题”。
4. **各模块验收路径**：在连着本机后端的真实 App 里按模块计划 §8 走，每步截图存 `05-测试/evidence/{模块}/`，和 §4 的设计图同视口并排。每一步写：过 / 不过 / 部分 / 没测，没测的写原因。
5. **对照接口改动总览查计划外的行为变化**，有就单独列出。

出了问题先判断属于谁：

| 问题属于 | 处理 |
|---|---|
| 后端不符合 `api.md` | 记下来，反馈给 Claude，在后端任务组加修复任务（B-xx） |
| 前端不符合 `api.md` | 记下来，反馈给 Claude，在前端任务组加修复任务（F-xx） |
| `api.md` 没规定，或规定错了 | 不改代码。记进问题清单，等用户决定后回技术规划改接口 |

- Codex **只修检验计划“只能改哪些文件”里列出的小问题**（编译错误、测试夹具、明显的笔误）；其余只记录。要改清单以外的文件，停下来问用户。
- **同一个问题最多修 3 次**，仍未解决就记进问题清单，继续后面的步骤。
- 不允许改 `api.md` 来迁就代码。
- Codex 自己新发现的问题，登记到问题清单，类型写“检验发现”。
- Codex 做完，把计划从 `待执行/` 移到 `待检验/`。Claude 看结果、修问题（每个端单独提交），写**复检计划**：只复检修过的地方，以及上一轮“部分”“没测”的步骤，已经“过”的不重测。结果看完、问题处理或登记完的计划移到 `已执行/`。

## 10. 统一联调和验收

1. 复检做完后，Claude 给用户一份报告，**第一项是接口改动总览的实际结果**：和总计划的总览逐行对比，一致的标“一致”，多出来的行逐条说明出处，说明不了的撤回。然后是每个模块的结果、问题清单（哪些要用户拍板）、被阻塞的模块和原因。
2. 问题清单里要用户决定的，**等用户处理**，不自己继续改。
3. **统一联调（M99）**：按每个模块的验收路径，从第一个模块走到最后一个，中间用同一份数据串起来；后端、前端的全量测试在这里跑一次。由用户自己做，或交给 Codex（计划同样放 `待执行/`）。
4. 统一联调通过后给出**接管五问**（规则写在哪、改它会动到哪、出问题从哪查、怎么撤回、哪些没验证）。**由用户确认**后，模块状态才能改为“通过”。

所有模块（含 M99）都“通过”后，版本 `README.md` 状态改为“测试”，进入 `06-测试.md`。

## 11. 执行中可以改哪些文档

| 文档 | 能不能改 |
|---|---|
| 模块计划 | 改任务状态、"结果"、§1 的阻塞记录、§11 审核记录；**§4 执行者不改**，由写计划的人在用户明确回复后补；改任务内容按 `04` 第 10 节 |
| 总计划 `开发计划.md` | 改模块清单表里本模块那一行（只用规定的词）、问题清单、调整记录。并行时只由主对话改 |
| `待执行/`、`待检验/` 里的计划 | Codex 只填“执行者填”的部分 |
| `05-测试/测试.md` | 填写测试的执行结果 |
| `01-产品/`、`02-设计/`、`03-技术规划/` | **执行者不改**。要改时停下来报告，由写计划的人改 |
| 仓库 `AGENTS.md` 的「常见坑」和仓库规范 | **执行者不直接加。** 发现值得记录的经验写进报告，由写计划的人和用户决定：加一条规则，还是改代码结构让这条规则不再需要 |

每次改完模块状态，更新版本 `README.md` 顶部的状态（第一个模块开工时改成“开发”），并运行一次 `scripts/progress.py`（第 12 节）。不要把测试通过数量、提交号清单、修复经过写进计划；放 git 提交和 `evidence/`。

## 12. 进度给用户看

- **当前对话**：Claude 开始写代码时，先按模块建任务列表，每个模块三项：后端、前端、自己审核。做完一项勾一项。并行的对话各建各的。
- **所有项目**：运行 `python3 /Users/soul/work/MakeCodePlanWord/scripts/progress.py`，它读各项目开发中版本的总计划模块表，生成工作台根目录的 `进行中.md` 和 `进行中.html`：项目、版本、模块、后端 / 前端 / 自审 / 检验、状态、分支、等谁。Claude 和 Codex 每次改完模块状态后运行一次。用户自己看：双击工作台根目录的 `看进度.command`，它会刷新并在浏览器里打开。不按版本走的项目（直接用 待执行 / 待检验 / 已执行 三个文件夹的），进度页列出三个文件夹里各有几份计划。
