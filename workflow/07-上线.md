# 07 上线

目标：把测试通过的版本安全地发出去，并记录上线后的表现。

产出：`vX.Y.Z/06-上线/上线记录.md`。第一次上架某个商店时，另看 `参考/首次上架清单.md`。

---

## 1. 上线前检查

- [ ] `05-测试/测试.md` 结论为"可以上线"（含用户对阻塞项的决定）
- [ ] 开发计划任务全部完成，或未完成的已移到 `backlog.md`
- [ ] 版本号、构建号已确定（构建号只增不减）
- [ ] 后端：部署顺序、数据库迁移、配置变更按技术方案"兼容与上线顺序"执行；旧版本 App 能兼容新接口
- [ ] 新增了数据收集、权限或三方 SDK 时：隐私政策、商店隐私表单、iOS 隐私清单已更新
- [ ] 付费相关改动：商店商品配置、价格、订阅说明已核对
- [ ] 商店素材（截图、描述）需要更新的已准备
- [ ] 用户可见的更新说明已写好（各语言）

## 2. 上线步骤

1. **出包**：按仓库 `AGENTS.md` 或规范目录里的构建说明出包（Android AAB、iOS IPA、后端部署包）。
2. **内部测试**：TestFlight / Google Play 内部测试轨道，安装正式包跑一遍冒烟用例。
3. **后端上线**：按部署顺序执行，迁移前先备份。
4. **提交审核**：被拒时把拒绝原因（Guideline 编号和原文）和处理记在上线记录。
   - 只改商店资料、审核备注的：改完用同一版本重新提交。
   - 要改代码的：版本还没在任何平台上线时，在开发计划加任务；已经在另一个平台上线时，放进下一个 patch 的修复单。
5. **分阶段放量**：App Store 分阶段发布 / Google Play 分阶段发布；放量期间观察第 4 节的指标。
6. **全量**：上线记录写上日期，进入 `08-归档.md`。

## 3. iOS 和 Android 分开上线

- 上线记录按平台分别记录。
- **第一个平台全量后就归档**，版本状态改为"已归档"。
- 另一个平台之后上线时，只在本版 `06-上线/上线记录.md` 补这个平台的上线记录和上线观察。这是归档后唯一可以改的地方。
- 另一个平台如果要先改代码再上，修复放进下一个 patch，可以直接用 patch 版本号首发。

## 4. 上线观察

在上线记录里记录放量期间和上线后一周的观察：

| 指标 | 上一版 | 本版 | 结论 |
|---|---|---|---|
| 崩溃率 | | | |
| 支付成功率 / 订单异常 | | | |
| 关键流程完成率 | | | |
| 接口错误率 | | | |
| 用户反馈 / 商店评论 | | | |

发现问题：

- 线上 bug → 按 `09-线上问题.md` 开 patch。
- 体验问题、新需求 → 写进 `backlog.md`。
- 严重问题 → 暂停放量；需要回滚的按上线记录的回滚预案执行。

## 5. 用户可见的更新说明

写在上线记录的「更新说明」一节，按语言分别写：

- 只写用户能感知的变化，分"新增 / 优化 / 修复"。
- 不暴露任务号、文件名、技术细节。
- 不写本版没有做的东西。
