# 02 设计

目标：每个涉及的页面都有明确的设计依据，开发照着做不用猜。

自己出稿固定顺序：**先出图片 → AI 自检 → 用户检查图片 → 通过后按图片绘制 Figma → 用户确认 Figma → 导出资源 / 技术规划**。图片检查和 Figma 确认是两个独立步骤，不默认合并。

## 产出（`vX.Y.Z/02-设计/`）

| 文件 | 是什么 |
|---|---|
| `设计说明.md` | **完整的设计索引**：设计系统（颜色、字体、组件）、Figma 文件和页面节点、出图和切图在哪、对稿规则。开版本时从上一版复制，本版有变化就直接改 |
| `设计计划.md` | **本版**：每个页面的设计来源（A / B / C），自己出稿时的风格基线、页面清单、出图提示词、出图记录、Figma 节点、确认记录 |
| Figma 稿 | 链接和节点写在设计计划和设计说明里，不放文件 |

图片和切图放工作区的 `design-assets/vX.Y.Z/`（或设计工作区），不放进版本文件夹。

## 1. 定设计来源

在 `设计计划.md` 第 1 节给每个涉及的页面三选一：

| 来源 | 什么时候 | 要做什么 |
|---|---|---|
| **A 外部已提供** | 设计师或合作方给了 Figma / 图片 | 做“接收检查”（第 2 节）；只有图片则先请用户检查，通过后补可编辑 Figma；已有 Figma 则接收检查后交用户确认 |
| **B 自己出稿** | 新页面或大改版，需要先看到样子 | 走第 3 节：先请用户检查图片，通过后才画 Figma；Figma 再确认后进入技术规划 |
| **C 不出稿** | 小改动、沿用现有组件和样式 | 不出稿；开发按现有设计系统实现，测试时截图验收 |

全部是 C 的版本，设计计划里写一句"本版不出稿"，直接进入技术规划。

## 2. A 外部已提供：接收检查

拿到稿子后检查一遍，缺的列给用户或设计方：

- [ ] requirements-list.md里涉及的每个页面都有稿子
- [ ] 每个页面的状态齐全：默认、加载、空、错误、无权限、弹框、成功和失败反馈
- [ ] 横竖屏、小屏、平板（如果支持）
- [ ] 多语言下长文案的表现（如果支持多语言）
- [ ] 切图和图标能拿到（导出格式、倍率）
- [ ] 稿子和产品文档的规则不矛盾；矛盾的登记到requirements-list.md的待确认决策

缺状态不一定要补稿，可以在产品文档里用文字说明，由开发按设计系统补齐。

接收检查不代替用户确认。只有图片时，沿用第 3 节的图片检查 → Figma 绘制 → Figma 确认顺序；已有可编辑 Figma 时，不要求倒回生成图片，但须登记来源与用户确认依据后才进入技术规划。

## 3. B 自己出稿

默认用 ChatGPT 网页版出图；在当前会话由 AI 出图时也执行同样的检查与确认。按下列顺序推进，每一步的结果写在 `设计计划.md`：

1. **定风格基线**（用户确认）：从参考来源（官网、竞品截图、旧稿）提取颜色、字体、圆角、阴影、按钮、卡片、图标和插画风格，写成具体数值。参考来源是网页时，直接读它的样式变量（CSS 变量、计算样式），比看截图准。
   - 还要补上参考来源里没有的：功能色（正确、错误、提示、警告）、特殊页面规则（例如横屏练习页谱面和键盘优先、装饰让位）、多语言和字体可用性（例如中文衬线字体在 Android 上没有，要不要内置）。
2. **列页面清单**：对照全量基线与本版 requirements.md / requirements-review.md 的涉及页面和弹框列出每页的方向、关键状态、是否有交互调整（对应requirements-list.md的 R 编号），并分批。
3. **出风格锚点**：先出 2～3 张最有代表性的页面（例如竖屏常规页、横屏练习页、付费页），按第 6 步交用户检查。候选风格可以先用图片比较，未决定的选项标为候选，不记成已确认。锚点通过只批准该风格及所列图片，不等于后续全部页面通过。
4. **写出图提示词**：每页一段完整提示词，用户在 ChatGPT 网页版里执行。写到 ChatGPT 不用猜的程度：
   - 尺寸和方向（竖屏 `852×1845`、横屏 `1845×852`，平面 UI 截图，不带手机外壳和场景）
   - 风格基线的具体数值（色值、字体类型、圆角、阴影）
   - 页面从上到下的结构、每个区块的内容和真实文案（取自产品文档，不让 ChatGPT 自编）
   - 本页展示哪个状态
   - 禁止项（不加需求里没有的功能、入口、Tab、角标；不用风格基线排除的元素）
   - 要上传哪张锚点图
5. **出图与落盘**：按 `{页面ID}-{状态}-r{轮次}.png` 命名，存到 `design-assets/vX.Y.Z/`。每页在设计计划记录轮次和结论。
6. **检查图片并等待用户**：AI 先检查比例、实际分辨率、文字、页面结构、状态覆盖及多余功能；固定文案遵循产品文档，动态数字只是示例。随后展示实际图片，请用户检查；逐页或逐批记录文件、轮次、AI 结论、用户结论、日期与直接依据。不合格按意见重出；未收到用户明确“通过”前保持“图片待用户检查”，不得创建对应 Figma 变量、组件或页面。
7. **仅按用户已通过图片绘制 Figma**：
   - 先建变量（颜色、字体、字号、间距、圆角、阴影）和组件（按钮、卡片、列表项、导航栏、Tab、输入框、弹框、标签），数值来自风格基线，不从图片里吸色。
   - 再按页面图画稿，用组件拼，不贴图。图片里的文字、数字和布局细节以产品文档为准。
   - 每页登记源图片文件和轮次、用户通过依据、对应 Figma 节点；未通过页面不混入绘制批次。图片变更后，受影响页面重新交用户检查，不沿用旧轮次批准。
8. **用户确认 Figma 稿** → 导出切图和图标。

不得默认跳过图片确认直接画 Figma。用户另行明确要求改变顺序时，先在设计计划记录具体范围和依据；“继续”、AI 自检通过或同意流程，不视为对未展示图片的批准。

规则：

- **开发以用户确认的 Figma 及其导出资源为准**；用户已通过的图片是 Figma 绘制与对稿依据，不代替可编辑稿。不能把整页图片贴入 Figma 当作画稿，也不能在运行时用整页截图代替 UI。
- 只改视觉的页面和有交互调整的页面分开标注；有交互调整的必须在requirements-list.md里有对应条目和验收标准。

## 4. 更新设计说明

设计确认后，直接改本版的 `设计说明.md`，让它反映这一版做完后的样子：

- 设计系统：风格基线的颜色、字体、形状规则（或写明"见 Figma 变量"）
- Figma 文件链接、每个页面的节点
- 出图、切图、图标的存放位置
- 每项资源的源图片轮次、Figma 节点、导出文件 / 格式 / 倍率、使用页面及代码目标路径；尚未导出的标待产出，不以旧图或占位图冒充完成
- 不再使用的旧稿标注"已废弃（vX.Y.Z 改版）"

## 5. 设计和业务规则冲突时

- 布局、视觉、组件位置、交互状态：以设计稿为准。
- 价格、次数、额度等动态数值：以服务端和配置为准，设计稿上的数字只是示例（见 `01` 第 2 节）。
- 固定文案或业务流程和已确认的产品文档冲突：以产品文档为准，并记录差异。除非用户要求，不修改设计文件。

## 6. 交给用户确认

在设计计划的“确认记录”分别登记图片检查和 Figma 确认。图片通过后仍处于“设计”；所需 Figma 稿获用户确认、资源交付范围明确后，版本 `README.md` 才改为“技术规划”。

设计还原度的检查放在测试阶段：关键页面截图和设计稿对比，记录差异和处理结论。
