## 三、规则和实际对不上的地方

### 1. 谁写代码：规则写的是 Codex，实际是 Claude

- 规则：Claude 写计划和审查，Codex 写代码（`05-开发.md`、P5、P6）。
- 实际：Claude（Opus）写代码，Codex 负责编译、跑测试、联调。11-25 你定的原话是“Claude 只做开发和代码审核，真实测试全部交给 Codex”。
- 后果：Claude 的环境没有 Gradle、Flutter、PostgreSQL。总检验计划里写着：后端测试“一个都没运行过”，网页端、手机端代码没跑过。也就是 6 个模块的代码是在一次都没运行的情况下写完并提交的。

### 2. 联调：规则是每个模块一次，实际是全部写完一次总检验

- 规则：每个模块后端 → 前端（假数据）→ 联调，通过后删假数据。
- 实际：11-24 你问“为什么不一口气把计划都做完，然后让 chatgpt 去做检测呢”，于是改成 M01～M06 全写完，再交一份总检验。总计划里也写了“前端开工时本模块后端已经做好，直接连本机后端，不做假数据”。
- 这是第 1 点带来的：写代码的 AI 跑不了程序，每个模块单独联调做不了；同一个 AI 先写后端再写前端，假数据也用不上。
- 代价：第一轮总检验的 44 项人工步骤里，过 20 项、部分 11 项、没测 13 项，不到一半。没测的大多卡在同一个问题上（没有主图的主体选不到，导入走不通），一个问题挡住了后面三个模块的步骤。

### 3. “待执行 / 待检验 / 已执行”三个文件夹：在用，规则里没有

### 6.1 开发阶段的新流程

```
开发计划审核通过
→ 打样（符合条件时）：走通主链路，Codex 实际运行，你确认方向
→ Claude 按模块写代码：后端 → 前端；每个模块写完自己审核，最多 3 轮，问题记下来
→ 全部模块写完（并行开发的先汇总）
→ Codex 检验：先冒烟，再核实 Claude 记下的问题，再跑测试和验收路径
→ 反馈给 Claude 修 → Codex 复检
→ 统一联调（你）→ 验收
```

### 6.2 打样

| 项 | 规定 |
|---|---|
| 什么时候必须做 | 满足任意一条：新项目搭框架；工作量超过 1 天；链路很长（跨三个以上环节，或要接外部服务、模型、支付）；用了以前没用过的技术或做法 |
| 做什么 | 只做一条最窄的主链路：从界面点一下，经过接口、数据库、外部服务，结果回到界面。不做界面细节、异常处理和其余功能 |
| 写在哪 | 总计划加一节“打样”：走哪条链路、要证明哪几件最没把握的事、不做什么 |
| 怎么算通过 | Codex 在本机实际运行，留下截图或日志；你看过，确认路线没偏 |
| 没通过 | 先回去改技术方案或计划，不开始写模块 |
| 不用打样的 | 小改动、在已经跑通的链路上加功能。计划里写一句“不打样”和原因 |

### 6.3 Claude 写代码和自己审核

- 一个模块先写后端、再写前端，两端分开提交。后端先做好，前端直接连后端，**不再做假数据**。
- 每个模块写完做代码审核，最多 3 轮。审核固定查四样：实际改动和接口改动总览对不对得上；每条 AC 有没有做到；有没有计划外的行为变化；有没有改计划没列的文件。
- 审核记录写在模块计划里：第几轮、发现了什么、改了没有。3 轮后还没解决的，以及 Claude 拿不准的，记进问题清单，类型写“待 Codex 核实”。
- 不停下来等你，继续做下一个模块。只有三种情况停下来问：要动总览以外的接口或表结构；涉及钱、权限、删除数据而计划没写；整份计划无法执行。

### 6.4 Codex 检验

- 一份检验计划覆盖全部模块，按顺序做：冒烟（编译、启动、主链路走通）→ 逐条核实 Claude 记下的问题 → 测试 → 各模块验收路径。冒烟不过就停，先反馈。
- 每个问题给出结论：属实 / 不属实 / 没法验证，附证据。Codex 自己新发现的另列。
- Codex 只修检验计划“只能改哪些文件”里的小问题，其余只记录，反馈给 Claude。

### 6.5 多任务并行

| 规定 | 说明 |
|---|---|
| 一个任务一个分支、一个目录 | 两个对话不在同一个目录里同时改代码。并行的任务各开一个 git 工作区（worktree） |
| 计划里写清谁能并行 | 模块计划加一行“会改的文件和目录”。两个模块有重叠就不能并行，按顺序做 |
| 公共文件提前分好 | 迁移脚本的版本号、多语言文件、路由表、`api.md`：在总计划里先分配好编号或归属，并行期间接口不改 |

| 汇总是单独一步 | 并行模块都写完后，由主对话按顺序合并分支、解决冲突、编译，然后才交给 Codex 检验 |
