## 2. 执行顺序

M01 → M02 → M03 → M04 → M05 → M06 → M07 → M08 → M09 → M10 → M11 → M12 → M13 → M14 → M16 → M17 → M99。M12（后台工程的邀请注册页）不依赖任何模块，随时可以单独做。M11（手机端）只依赖 M04～M06 的后端任务，后端做完即可与网页端并行。

可并行：**后端任务在 M01、M03、M04、M05、M06 里**（M04～M06 是 B-10 漫剧分析与片段流程），后端执行者可以先一次做完这几个模块的后端任务（只改后端仓库），网页端执行者同时按顺序做前端任务（新接口用 `api.md` 样例做假数据）。联调仍按模块顺序。

规范：网页端代码以仓库 `.cursor/rules/`（M01 F-00 放入，来源是工作台 `templates/repo-rules/flutter/`）为准；模块计划里写的文件路径、类名与规范不一致时按规范做，并在任务“结果”里写明。

测试范围：后端任务只跑任务里写的那几个测试（只覆盖本任务改到的模块），不跑全量的 `./gradlew test`、`./gradlew build`；全量测试只在 M99 统一联调做一次（2026-11-16 用户定）。

**执行方式（2026-11-16 用户选 B：先写代码，最后联调；目的是快点开发）**

1. **写代码阶段**：M01 → M12 按顺序，每个模块只做后端任务和前端任务，做完填 §11 交付报告，不停，接着做下一个。各模块的 J-01 都不做。
2. **遇到问题分两类**（自己刚写错的代码改对不算问题；验证时发现、一时修不好的才算）：
   - 不挡路的：记进第 5 节问题清单，不修，继续往下做。
   - 挡路的：停下来修；同一个问题最多修 3 次，还不行就停下报告给用户，不绕过。
3. **挡路的判断**，满足任意一条就算：编译不过或工程、本机后端跑不起来；登录、注册走不通；数据库迁移执行失败；后面的任务或模块要用的接口、公共组件做不出来，或返回的内容和接口文档对不上；必须改计划以外的文件才能继续。样式和设计图有差别、某个状态或文案不对、单个功能失败但不影响别的页面，都不算挡路。拿不准时看“后面的任务会不会用到它”，会用到就按挡路处理。
4. **整体联调阶段**（全部写完后，见 M99）：先按 M01 → M11 的顺序一个功能一个功能过各模块的 J-01（这时才删假数据和开关），再逐条过第 5 节问题清单，最后做 M99 的走查。

规则：每个模块依次做后端任务、前端任务；联调（J-01）全部挪到最后（见上面“执行方式”）。**后端已经有的接口，前端任务直接连本机启动的后端边做边调试联调，不连测试环境、不写假数据（2026-11-16 用户定）；只有后端还没做出来的新接口先用假数据，后端新接口做好以后前端关掉假数据开关、连本机后端自己走一遍，假数据文件和开关到整体联调通过后再删。**每一端做完，执行者要填模块计划 §11“交付报告”（后端：新增 / 修改了哪些接口；前端：完成了哪些页面与功能；有大模型调用的：调试程序怎么运行），用户按 §11.4 手动检测。写代码阶段遇到问题按上面“执行方式”分挡路 / 不挡路处理；整体联调阶段同一个问题最多修 3 次，仍未解决就登记到第 5 节，继续下一个模块的联调。现有接口直接连测试环境，不做假数据；新接口的假数据在对应模块联调通过后删除。

- 上线顺序：后端（含迁移）先上测试 → 网页端打开 `X-OS-Type` 开关联调 → 后端上正式 → 运维配置（C-02 部署位置、C-03 OSS 跨域、C-04 支付宝、C-06 真实 IP）→ 网页端上正式。见技术方案 §8。
- 迁移：公共新增 `common/V5.1__user_password_credentials.sql`（M01）；漫剧新增 `catdrama/V5.2__catdrama_asset_plan_and_shots.sql`（M04，用户 2026-11-16 决定新增文件、不改 `V4.19`）。`V5.2` 要在 `V5.1` 之后合入。测试环境和本地库启动时自动执行，不需要手工同步。回退代码时新表、新字段都保留。
- C-06 未配好时，网页注册限制会把所有网页用户当成同一个 IP；上线检查必须核对。
- 旧版本手机 App：账号、支付相关的返回不变；**漫剧分析与片段流程变了**（分析完不再有片段、剧集多了 `SHOTS` 阶段），旧版手机端走不通这一段，后端要和手机端新版（M11）一起上线（技术方案 §8）。 已经装在用户手机上的旧版不升级就走不通素材之后的流程（M11 §9 列了三处），上线前由用户决定是否用现有的强制更新。
