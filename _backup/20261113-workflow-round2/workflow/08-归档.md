# 08 归档

目标：版本上线后，把已上线的本版增量合入全量当前产品文档、沉淀测试成果、冻结版本文件夹，让下一版能放心地从这里开始。

什么时候做：版本在第一个平台全量上线后（见 `07` 第 3 节）。patch 的归档见 `09` 第 5 节。

清单写在 `06-上线/上线记录.md` 的「归档」一节，由 AI 执行，用户审核。

## 步骤

1. **核对文档和实际上线的一致**
   - 本版 requirements.md：对照 requirements-list.md 的 R / AC，只合入实际上线的需求；取消、延期、未交付项保留追溯并登记 backlog，不混入线上基线。
   - `⚠️ 待确认` 还没关闭的，留在原处，并在项目 `backlog.md` 登记一条，下一版处理。
   - `03-技术规划/`：`api.md`、`data-model.md` 和实际上线的代码一致（接口路径、字段、迁移脚本版本号）。
   - `02-设计/设计说明.md`：Figma 链接和节点是最终版。
2. **合并到全量当前产品文档**：
   - 按 requirements-list.md 的 R 逐项核对 requirements.md，将实际交付的变化写到 `当前产品文档/` 对应模块；新增功能补模块 / 页面索引，删除功能核对入口、状态和数据处置。
   - 保留所有未改功能，更新基线版本与日期；核对 R / AC、页面和本地链接，用户审核 diff。不能把增量文件或四文档目录整体覆盖到当前产品文档。
   - 新项目首次归档：从已交付的首版 requirements.md 整理第一份全量基线，可按模块分册；校正链接与版本信息。
   - `scripts/update-current-doc.sh` **仅兼容旧全量格式**；遇到四文档增量版本会拒绝执行，不做替换。新格式按上述步骤有依据地合并。
3. **测试沉淀到项目 `testing/`**
   - 本版新增用例中值得长期保留的，合并进 `testing/regression.md`，标出冒烟用例。
   - 本版发现的新风险维度，补进 `testing/risk-checklist.md`，写明来源。
4. **backlog**：本版"已排入"的条目改为"已完成 vX.Y.Z"；延期的改回"待评估"并写原因；测试遗留的 P2、P3 缺陷登记进来。
5. **状态**：版本 `README.md` 状态改为"已归档"，写上日期。
6. **项目 `README.md`**：线上版本改为本版；版本列表加一行（版本、上线日期、一句话、文件夹）；开发中版本更新。
7. **其他开发中的版本**：复核它们引用的基线版本，检查其增量与新基线是否冲突；只同步受影响需求、确认状态和技术文档，不把全量再复制进去。
8. **打 tag**（用户执行，或用户同意后由 AI 执行）：
   - 工作台仓库：提交工作区文档，打 `{appCode}-vX.Y.Z`
   - App 仓库：`vX.Y.Z`
   - 后端仓库（本版有改动时）：`{appCode}-backend-{后端版本号}`
9. **冻结**：从此这个版本文件夹不再修改（另一个平台后上线时补上线记录除外）。
10. **掌控度体检**（结果写进归档摘要；要做的事登记到 `backlog.md`，不改已冻结的版本文件夹）：
    - 后端仓库有模块与接口清单的，重新生成一次（例如 `python3 docs/module-interfaces/generate.py`），看“已知越界”的数量有没有增加。
    - 降级演练：抽一个真实的小任务，用次一档的模型或自己动手完成。做不下来，就把“降低理解成本”排进下一版。
    - 规则体检：仓库里每次必读的规则是否仍在 100 行以内；本版新加的规则，能不能改成代码结构或检查脚本。

完成后，AI 给出"归档摘要"：当前产品文档改了哪些文件、测试沉淀了哪些用例和维度、backlog 和 README 改了什么、有没有同步到其他版本、掌控度体检的结果。用户对照 git diff 审核。
