# 06 测试验收（test.md）

目标：上线前发现问题，尤其是"页面看起来没问题，数据其实是错的"这一类。

## 1. 测试分三层

| 层 | 测什么 | 谁写、谁跑 | 什么时候 |
|---|---|---|---|
| **自动化测试** | 业务规则、接口、数据读写、状态流转 | 执行 AI 在每个任务里写，开发时就跑 | ⑤ 开发执行 |
| **数据链路检查** | 钱、账号、权益、同步这类跨系统流程，每一环的数据是否一致 | 用户或 AI，可以查库、看后台、看日志、抓包 | ⑥ 测试验收 |
| **人工 / 真机** | 必须人来做的：真机、实体外设、真实商店购买、视觉还原、手感 | 用户 | ⑥ 测试验收 |

能自动化的不要留给人工；人工用例只留真正需要人的部分。

## 2. 用例从哪里来

- **验收标准（AC）**：`changes.md` 里每条 AC 至少对应一条用例。
- **高风险清单**：`scope.md` 勾选的领域，把 `doc/testing/risk-checklist.md` 里对应的维度逐条转成用例或检查项。
- **回归集**：从 `doc/testing/regression.md` 选出本版要跑的回归范围（涉及模块的全部用例 + 所有冒烟用例）。

用例在 ④ 写计划时就写好，不是开发完再补。

## 3. test.md 的结构

模板见 `templates/doc/versions/_template/test.md`：

1. **测试范围**：本版涉及模块、勾选的高风险领域
2. **环境矩阵**：设备 / 系统、地区 / 币种、语言、账号类型、网络、后端环境。只列本版需要覆盖的组合。
3. **新增用例**：本版新写的用例，格式见第 4 节
4. **数据链路检查**：见第 5 节
5. **回归范围**：引用 `regression.md` 的用例 ID，不复制全文
6. **执行记录**：每轮一张表——构建号、日期、执行人、各用例结果
7. **缺陷**：缺陷表（见第 7 节）
8. **结论**：是否可以发布、遗留问题、用户的决定

## 4. 用例格式

```markdown
### TC-12 巴西区购买年卡，订单币种正确
- 关联：AC-03-1　优先级：P0　层：数据链路 + 人工
- 环境：iOS 真机、App Store 沙盒巴西区账号
- 前置条件：账号无有效会员；后台可查订单
- 步骤：
  1. 进入会员页，确认年卡价格显示为 R$
  2. 购买年卡并完成支付
  3. 进入"我的 → 订单"
- 预期（界面）：
  - 订单列表显示 "R$ xx,xx"，与商店扣款一致
- 预期（数据）：
  - 接口 GET /orders 返回 currency=BRL，amount 与商店回执一致
  - 数据库 order 表该订单 currency=BRL
  - 后台订单页显示 BRL
- 验证方式：界面截图 + 接口返回 + 后台截图
```

要求：

- **"预期（数据）"不能省**：只要涉及钱、账号、权益、同步、配额，就要写清存了什么、接口返回什么。
- 步骤一步一个动作，可以照着做。
- 预期可观察、可判断对错。不写"系统正常""结果正确"。
- 一条用例只验证一个目标。
- 优先级：P0 核心链路和资金数据；P1 主要功能；P2 边界和兼容；P3 体验。

## 5. 数据链路检查

钱、账号、权益、同步这类流程跨多个系统，任何一环字段丢失或默认值不对，页面都可能看起来正常。对这类流程，逐环核对：

```
商店 / 第三方回执 → App 本地 → 接口请求 → 服务端处理 → 数据库 → 接口返回 → App 展示 / 后台展示
```

在 `test.md` 里每条链路一张表：

| 环节 | 检查字段 | 期望值 | 实际值 | 证据 |
|---|---|---|---|---|
| 商店回执 | currency / price | BRL / 129.90 | | |
| 服务端入库 | order.currency / amount | BRL / 129.90 | | |
| 订单接口 | currency / amount | BRL / 129.90 | | |
| App 订单列表 | 显示 | R$ 129,90 | | |
| 后台 | 币种 / 金额 | BRL / 129.90 | | |

多地区的产品，至少用两个不同币种的地区各走一遍（例如美区 + 一个非美元地区）。

## 6. 通过标准

- 新增用例和回归范围中，P0、P1 全部通过。
- 勾选的高风险领域的检查项全部完成。
- **"未执行"不等于"通过"。** 缺设备、缺账号、缺环境的用例标"阻塞"并写原因，由用户决定能否带着阻塞项发布，决定写进 `test.md` 结论。
- 自动化测试通过，不能代替必须人工执行的真机、真实商店、实体设备用例。
- P2、P3 缺陷可以留到下个版本，但要登记进 `backlog.md`。

## 7. 缺陷怎么处理

- 缺陷登记在 `test.md` 缺陷表：ID（`D-序号`）、标题、严重度、关联用例、复现步骤、期望、实际、状态。
- 修复作为 `plan.md` 的新任务（"T-12 修复 D-03：……"），按 ⑤ 执行。
- 修复后在新构建上重跑原用例和相邻的正常路径；原失败记录保留，在执行记录里新增一轮。
- 不需要为每个缺陷单独建文件，除非缺陷需要附大量截图（放 `versions/vX/evidence/`）。

## 8. 回归集和高风险清单的维护

- **发布时**：本版新增用例中值得长期保留的，合并进 `doc/testing/regression.md`（见 `07`）。
- **线上出 bug 时**：
  1. 往 `regression.md` 加一条能复现这个 bug 的用例。
  2. 想一想"这是哪一类问题"，往 `risk-checklist.md` 对应领域加一条检查维度，写明来源（哪个版本、哪个 bug）。
- 清单只增不乱：重复的合并，过时的标注原因后删除。

## 9. 自动化辅助（可选）

- 单元测试 / 接口测试：Flutter 用 `flutter test`，Java 用 `./gradlew test`。数据断言写在这里最划算。
- 界面冒烟：Web / Flutter Web 用 Playwright；模拟器或真机用平台工具或 Python 脚本辅助点击和截图。
- 自动化脚本命名带用例 ID，输出截图或日志；脚本不能代替用例文档。
- 证据放 `versions/vX/evidence/`，文件名带日期、平台、构建号、用例 ID。
