# 11 旧项目迁移（v1 工作区 → 新结构）

适用：`workspace-registry.json` 中 `flow` 为 `"v1-legacy"` 的项目，也就是工作台 `projects/{项目名}/` 下有 `workflow.md`、`change-plan.md` 的项目。

原则：**迁移过程中不删旧文件，不编造内容。** 拿不准的内容标 `⚠️ 待确认` 交给用户。旧工作区在迁移完成、用户确认后再按第 7 步清理。

迁移的结果：项目有一份 `当前产品文档/`（线上已完成的功能），线上版本有一个版本文件夹（产品文档、设计说明、技术文档、上线记录），之后的功能版本生成四份产品增量文档，设计和技术文档可以复制。

## 步骤

### 1. 确认基本信息（问用户）
- 线上实际版本号是多少（以商店为准）
- 现在有没有正在开发、还没上线的内容

### 2. 盘点旧资料
列出所有需求和技术来源，标出每份的状态：
- PRD（可能在工作台外，比如单独的设计工作区）
- 增量需求和契约（旧流程里常写在 `02-技术方案/*.md`）
- `change-plan.md` / `change-log.md` 中的变更：哪些已上线、哪些只是本地完成、哪些待审核
- 技术文档：`tech-plan.md`、`flutter-tech.md`、`java-tech.md`、开发计划
- 测试：人工用例、执行记录、缺陷记录

### 3. 建当前产品文档和线上版本的文件夹（只写线上已有的内容）
1. `scripts/init-project.sh <工作区> <项目名>` 生成 `README.md`、`backlog.md`、`testing/`。
2. 手动建 `vX.Y.Z/`（线上版本号），不用 `new-version.sh`：
   - **`01-产品/2-vX.Y.Z产品文档/`**：把 PRD + 已上线的增量需求按模块合并，写成"现在是什么样"。同一条规则在多份文档里说法不同时，以最新的、用户确认过的为准；判断不了的标 `⚠️ 待确认`。已实现但没上线的内容不写进来，放到第 5 步。迁移的线上基线不补写需求分析、产品评审版和检测报告；这是旧全量格式的迁移例外；之后的新功能版本只生成 requirements-list.md、requirements.md、requirements-review.md、detection-feedback.md。
   - **版本 `README.md`**：状态"已归档"，注明"迁移时整理的线上基线"。
   - **`02-设计/设计说明.md`**：登记设计稿、参考图、切图的位置。
   - **`03-技术规划/`**：把技术方案、前后端技术文档、接口契约合并成 `architecture.md`、`api.md`、`data-model.md`，只保留当前有效的。
   - **`06-上线/上线记录.md`**：版本号、上线日期、构建号（能查到的），旧测试记录的位置。
   - 没有开发计划和测试记录的，不建 `04`、`05`。
3. **`testing/regression.md`**：从旧人工用例整理，去重，标出冒烟用例；涉及钱、账号、权益的用例补上"预期（数据）"。
4. **`testing/risk-checklist.md`**：从模板开始，补上这个项目历史上出过的问题。
5. **`当前产品文档/`**：用 `scripts/update-current-doc.sh <工作区> vX.Y.Z` 从线上版本的产品文档生成。
6. **`README.md`**：线上版本、版本列表（能查到的）。

### 4. 迁移编码规范
编码规范留在代码仓库（规范目录如 `.cursor/rules/`），不搬进工作区。

1. 修正规范里引用旧流程的地方（`workflow.md`、`change-plan.md`、旧 `projects/...` 路径），改成工作区里的对应位置。
2. 按 `templates/repo/AGENTS.md` 写仓库根 `AGENTS.md`（写明工作区的绝对路径），加 `CLAUDE.md`。把最关键的规则提炼成「硬规则」，其余登记到「规范索引」。仓库已有 `AGENTS.md` 并正确索引了规范时，只加"文档与开发流程"一节、补 `CLAUDE.md`。
3. 多 App 共用的后端仓库，在它的 `AGENTS.md` 里加一节，写明这个 App 的工作区。
4. 代码仓库里原有的产品文档、计划文档搬到工作区，仓库里只留一份 `doc/README.md` 指向工作区。

### 5. 安置进行中的事
- 已实现但未上线的 → 用 `new-version.sh` 开下一个版本，写进它的 requirements.md 和 requirements-list.md，开发计划中对应任务标"完成（迁移前已实现）"。
- 线上 bug 修到一半的 → 开 patch，写进修复单。
- 未执行的测试 → 对应版本的 `05-测试/测试.md`。
- 想法、延期事项 → `backlog.md`。

### 6. 收尾
1. 在旧 `projects/{项目名}/workflow.md` 最顶部加一行：`> 已于 YYYY-MM-DD 迁移，当前文档见 projects/{项目名}/README.md。本工作区只读。`
2. `workspace-registry.json`：`flow` 改为 `"v2"`，填好 `workspace`。
3. 交给用户审核 `当前产品文档/` 和线上版本的 `03-技术规划/`，重点看 `⚠️ 待确认`。
4. 用户确认后，在工作台仓库提交，并打线上版本的 tag（例如 `solfeggio-v2.1.0`）。

### 7. 清理旧工作区（用户确认后才做）
1. 找出新文档里还在引用的旧文件，挪进 `history/v1/`（保留原来的子目录），并把引用路径改过去。
2. 其余 v1 文件逐项列给用户：大小、用途、有没有进过 git。**没进过 git 的文件删了就找不回来**，大的截图和日志由用户决定直接删还是先打包。
3. 用户确认后删除，更新项目 `README.md`，`workspace-registry.json` 里 `legacyWorkspace` 改为 `null`。

## 迁移时的注意

- 仓库里已经有按模块拆好的产品文档时，直接放进线上版本的产品文档：只调整文件位置和链接，加一段说明，不重写正文。
- 发现已上线、但产品文档里没写的内容，写在对应模块末尾的「迁移补入（⚠️ 待确认）」一节，等用户确认后再并入正文。
- 接口清单和表结构可以从代码自动提取（Controller 的路由注解、App 实际调用的路径、迁移脚本），比照抄旧技术文档可靠。
- 有其他 AI 会话正在工作时，不要移动或改写它正在编辑的文件；等它结束再移动。
- 代码仓库里被其他仓库或规则引用的测试记录、配置说明原地保留，在工作区 `README.md` 里登记为"代码仓库里的相关文件"。
- 旧状态里的"done（本地完成，未上线）"不算已上线，不写进当前产品文档。
- 旧 `archive/` 只用来核对历史，不搬进新结构。
- 测试证据（截图、日志）不搬进新结构。
