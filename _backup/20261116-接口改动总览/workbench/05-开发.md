# 05 开发

目标：按已审核的模块计划，**后端、前端分开实现，各自只对接口文档负责；两端做完再联调**。条件不具备就停，不猜；**每个界面都照着设计依据（Figma 节点或设计稿 / 设计图）做，没有设计依据的界面不做**。联调时同一个问题最多修 3 次，仍未解决就记进问题清单、继续下一个模块；全部模块做完后统一报告，问题处理完再做统一联调。

## 1. 开始前（每次新会话都要做）

1. **读代码仓库根目录的 `AGENTS.md`**（Codex、Cursor 会自动加载；Claude Code 通过 `CLAUDE.md` 导入）。里面写着项目工作区的路径。
2. 读工作区 `README.md` 找到开发中版本，读该版本 `04-开发计划/开发计划.md`（总计划），**只看模块清单表**，确认这次要做的是哪些模块、哪一组任务（后端 / 前端 / 联调）。
3. **一次只读正在做的那一个模块计划** `04-开发计划/模块/Mxx-*.md`；做完一个模块再读下一个。不通读 `05-测试/` 的历史记录。线上问题读 `修复单.md`。
4. 确认模块状态是"已审核"或"执行中"。**不是的话不写业务代码**，只可以读代码、回答问题、帮忙写计划。
5. 按 `AGENTS.md` 的「规范索引」读本模块相关的规范；换到另一个仓库做下一组任务之前，先读那个仓库的 `AGENTS.md`。
6. **复核开工条件**（第 2 节），设计核对第一个做。**核对完、没有缺失之前，不写前端代码。** 后端任务不涉及界面，可以先做。

> 工作台里的 `templates/repo-rules/` 只是新项目的模板。编码时以**代码仓库里的规范**为准。

## 2. 开工条件复核

对着模块计划 §1 逐项**实际检查**，不是读一遍计划里写的"已满足"：

- **设计（最先做）**：
  1. 实际打开 §4 每一行的设计依据：Figma 节点用 Figma 工具读取，设计图文件实际打开查看。读不到、打不开就算缺。
  2. 对照本模块的 AC 和 §8 验收路径，找出用户会看到、但 §4 没有列的界面或状态（弹框、提示、空状态、错误状态等）。
  3. 把缺失、打不开、和计划描述对不上的**全部汇总，一次性报告给用户**，写成「设计缺失清单」：缺哪个界面 / 状态、对应哪条 AC、影响哪些任务、建议。
  4. 清单为空才能开始做前端任务。
- **外部条件**：执行计划里写的验证方法（例如请求一次测试接口），确认账号、Key、环境可用。
- **前置模块**：看总计划里依赖模块的联调是“通过”。依赖的模块联调“有问题”时，本模块标“阻塞”并跳过，先做下一个模块。

任何一项不满足：

1. 在模块计划 §1 把该项改为"阻塞"，写清缺什么、需要谁提供。
2. 总计划里本模块状态改"阻塞"。
3. 不写该模块受影响部分的代码（缺设计时是前端任务和联调），计划没写明的别猜。只执行这一个模块时：向用户报告并停下。连续执行多个模块时：写进报告，继续做不依赖它的下一个模块。

## 3. 界面开发规则

- **每个界面都必须照着 §4 的设计依据做**（Figma 节点或设计稿 / 设计图），开发时打开对照，不凭记忆、不凭描述。
- §4 里没有的界面、状态、弹框、提示、组件、图标：**一律不做**，包括"临时的""占位的""先做个简单版"。不"参考类似页面"，不自己设计，不用近似图替代。
- 缺失应该在开工前的设计核对（第 2 节）里全部发现。**开发中途仍发现缺界面，说明核对漏了：整个模块停下**（模块状态改"阻塞"），报告缺哪个界面或状态、对应哪条 AC、影响哪些任务、建议（补稿，或沿用哪个现有页面）。不能先做别的、回头再补，也不能自己先做一个等用户改。
- 用户补稿，或明确回复"沿用某页面"后，由写计划的人写进 §4（含原话和设计图），再继续。
- 图标、插图从对应 Figma 节点或设计切图导出 1x / 2x / 3x，不得自己画或拼接。
- 业务动态内容（文案、数据）和设计示例不同时，以业务为准，在"结果"里写一句不同之处；布局、间距、颜色、字号按设计稿。

## 4. 每个任务的循环

1. 把任务状态改为"进行中"。
2. 按"具体做法"实现。只改"仓库与文件"里列出的文件；要动其他文件，先停下来说明原因。**做后端任务不改 App，做前端任务不改后端。** 发现另一端或接口文档有问题，写进任务“结果”和执行报告，不改，留到联调处理。
3. 跑任务里写的验证命令，加上仓库 `AGENTS.md` 规定的通用验证命令（例如 `flutter analyze`）。**后端只测本任务改到的模块**：只跑任务里写的 `./gradlew test --tests '…'`，确认编译用 `./gradlew compileJava compileTestJava`；不跑不带 `--tests` 的 `./gradlew test`，也不跑 `./gradlew build`（会跑全量测试）。全量测试只在统一联调（M99）做一次。后端任务按 `api.md` 的样例做接口测试，并核对数据库里的数据；前端任务的数据只用 `api.md` 的样例做成的假数据。
4. **界面核对**（有界面的任务）：在真实运行的 App（模拟器即可，不是 Widget 测试夹具）里打开各状态，与 §4 的对照用设计图同视口并排截图，截图放 `05-测试/evidence/{模块}/`。有差异的，在"结果"里写：已修 / 保留及原因。**不能写"已对照"却没有截图。**
5. 验证通过后，任务状态改为"完成"，"结果"最多两行：做了什么、提交号；证据路径。
6. 建议每个任务提交一次，提交信息带版本号、模块号、任务号，例如 `v2.2.0 M02 B-03: 订单保存商店实际币种`。是否由 AI 提交，按用户习惯。

## 5. 遇到计划外情况

以下情况**停下这个模块并报告**，不要自己扩展范围：

- 计划写的文件或方法不存在、和描述不一致
- 需要修改"不改动范围"里的内容
- **设计稿缺失，或和计划不一致**
- **产品规则不明确、AC 之间矛盾、需求没有定义的行为**
- 实现中发现需求有漏洞，或接口、数据契约不够用
- 验证失败，且原因不在本任务范围内
- 需要新增依赖、改数据库结构、改配置，而计划没写
- 需要新增或改变模块计划 §5 接口变化清单以外的接口、表结构或流程推进方式
- 同一个问题修 3 次仍未解决：停止继续尝试，记录现象、证据、三次各做了什么和判断的原因。联调里遇到的按第 6 节记进问题清单并继续下一个模块
- 外部条件失效（Key、环境、渠道）

报告内容：哪个模块哪个任务、发现了什么、建议怎么做、需要谁决定。

连续执行多个模块时：把这个模块标“阻塞”、原因写进总计划，继续做不依赖它的下一个模块，最后一起报告。需要动接口变化清单以外的接口或表结构，或者涉及钱、权限、删除数据而计划没写的，立即停下来问。

**不得在对话里或计划里直接改产品规则。** 用户决定后，由写计划的人先改 `requirements.md`（涉及设计、技术的一并改），再改计划（`04` 第 10 节），然后继续执行。

## 6. 联调

一个模块的后端任务和前端任务都“完成”后做，每个模块一次。联调不写新功能。

1. App 关掉假数据开关，连真实的后端。按模块计划 §8 的验收路径从头走一遍，每步截图存 `05-测试/evidence/{模块}/`。
2. 出了问题先判断属于谁，再修：

   | 问题属于 | 处理 |
   |---|---|
   | 后端不符合 `api.md` | 在后端任务组加一个修复任务（B-xx），回后端仓库改 |
   | 前端不符合 `api.md` | 在前端任务组加一个修复任务（F-xx），回 App 仓库改 |
   | `api.md` 没规定，或规定错了 | 不改代码。记进问题清单，等用户决定后回技术规划改接口 |

   **不允许为了让联调通过而两边一起改，也不允许改 `api.md` 来迁就代码。**
3. **同一个问题最多修 3 次。** 3 次仍未解决：联调标“有问题”，模块状态改“阻塞”，把问题写进总计划的问题清单（现象、证据、三次各做了什么、判断的原因、属于后端 / 前端 / 接口文档），然后**继续做下一个模块，不停下来等**。
4. 联调通过：删除本模块的假数据、开关分支和相关代码，搜索确认没有残留；联调标“通过”，模块状态改“待验收”。

## 7. 全部模块做完以后

1. 给用户一份报告，**第一项是接口改动总览的实际结果**：和总计划里的总览逐行对比，一致的标“一致”，多出来的行逐条说明出处，说明不了的撤回。然后是：
   - 每个模块的后端、前端、联调结果；
   - 问题清单：每条写清哪个模块、现象、证据、试过什么、判断的原因、建议怎么改；
   - 假数据：哪些模块已删除，哪些因为联调有问题还留着；
   - 被阻塞的模块和原因。
2. 问题清单为空：直接进入统一联调。不为空：**等用户处理**，执行者不再自己继续改。用户处理完，再进入统一联调。
3. **统一联调（M99）**：确认所有假数据已删除、App 连的是真实后端；按每个模块的验收路径，从第一个模块走到最后一个，中间用同一份数据串起来，每步截图。出了问题同样先判归属、最多修 3 次。
4. 统一联调通过后给出报告，包含**接管五问**（规则写在哪、改它会动到哪、出问题从哪查、怎么撤回、哪些没验证）。**由用户确认**后，模块状态才能改为“通过”。

所有模块（含 M99 统一联调）都“通过”后，版本 `README.md` 状态改为“测试”，进入 `06-测试.md`。

## 8. 执行中可以改哪些文档

| 文档 | 能不能改 |
|---|---|
| 模块计划 | 只改任务状态、"结果"和 §1 的阻塞记录；**§4 执行者不改**，由写计划的人在用户明确回复后补；改任务内容按 `04` 第 10 节 |
| 总计划 `开发计划.md` | 只改本模块那一行的状态，以及问题清单 |
| `05-测试/测试.md` | 填写自动化测试的执行结果 |
| `01-产品/`、`02-设计/`、`03-技术规划/` | **执行者不改**。要改时停下来报告，由写计划的人改 |
| 仓库 `AGENTS.md` 的「常见坑」和仓库规范 | **执行者不直接加。** 发现值得记录的经验写进执行报告，由写计划的人和用户决定：加一条规则，还是改代码结构让这条规则不再需要 |

不要把测试通过数量、提交号清单、修复经过写进计划；放 git 提交和 `evidence/`。

## 9. 审查（写计划的人做：全部模块做完后一次，统一联调后一次；也可以按模块提前做）

- **先对接口改动总览**：自己对照 git diff 列出实际的接口改动，和计划最上面的总览逐行对比，再看下面各项
- 改动是否只在计划列出的文件内
- 是否遵守了「已读规范」中列出的条款
- 是否复用了计划指定的组件，有没有重复造轮子
- 实现和 `api.md`、`data-model.md` 的契约是否一致（字段名、类型、币种、时区）
- 测试是否真的覆盖了对应的 AC，而不是只测了正常路径
- 界面截图是不是真实运行 App 拍的、是不是和设计图同视口、差异说明是否成立
- 开工前的设计核对是否做了、缺失是否在写代码之前一次性报告
- 有没有出现 §4 之外的界面、状态、组件或图标（有就退回删除）
- 验收路径的每一步是否都有截图
- 有没有"顺手"的改动
- 接口变化是否都在模块计划 §5 的清单里（对照 git diff 里的 Controller、请求响应对象、迁移脚本和接口文档）
- 做后端任务时有没有改 App，做前端任务时有没有改后端
- 联调问题的归属判断是否成立；有没有为了让联调通过而两边一起改，或改接口文档迁就代码
- 联调通过的模块，假数据、开关分支和相关代码是否删除干净
- 有没有把产品需求里“用户确认”的步骤做成自动推进
- 新增的校验是不是在保护钱、权限、用户内容、审核、外部输入或流程状态；不是的退回删除

发现问题就在对应任务的"结果"里记下，并新增修正任务或退回重做。
