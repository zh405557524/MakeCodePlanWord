# 需求文档检测 - 累计反馈

> 记录需求文档检测阶段的用户意见、修订意图与闭环情况。
> 规则来源：`.cursor/rules/03-需求文档检测.mdc`

## 历史记录

### 2026-04-01 第1轮检测后修订

- 用户要求按检测报告修订 PRD v1.3。
- 已落实事项：
  - 为 `PlanEditor` 增加独立功能描述。
  - 增加统一接口约定。
  - 补充注册、登出、`master-plans`、终止计划、`GET profile` 等能力说明。
  - 补充设计稿序号 19 的说明。

### 2026-04-01 第2轮检测用户补充

- 当前阶段不做登录系统。
- 登录能力不从产品中永久删除，但仅作为后续可扩展模块保留，不纳入当前版本范围。
- PRD 需要补充“整体 App 描述”，至少包括：
  - 开屏页 -> 主页 -> 主页 4 个主界面 -> 计划总体介绍 -> 计划详情 -> 计划编辑 的整体交互链路。
- PRD 需要按 UI 页面详细描述功能，至少包括：
  - 页面配色方案。
  - 图标选择。
  - 对应功能点。
  - 交互流程。
- 用户希望最终文档达到“合格的商业化 App 产品文档”水平，可作为后续技术方案和实现输入。

### 2026-04-01 第3轮检测用户补充

- 用户认可当前版本“像一个正常的产品文档”。
- 用户强调这一步的标准应被保留：文档必须是真正给人看的、能让人读懂的产品文档。
- 用户认为当前交互流程描述仍然过于简略。
- 本轮重点修订方向：
  - 把交互流程写清楚。
  - 不只写页面跳转关系，还要写明用户在每一步看到什么、执行什么操作、系统如何反馈、然后进入哪里。
  - 让主链路和关键分支都具备可阅读性与可执行性。

### 2026-04-01 第4轮检测用户补充

- App 在无网络情况下也必须可以本地创建和使用计划。
- 计划功能不依赖后端接口数据才能成立。
- 前端需要本地保存计划相关数据。
- 后端接口依然需要保留，用于与前端数据保持更新和同步。
- 产品文档需要明确“离线优先，本地可用，同步补偿”的原则。

### 2026-04-01 第5轮检测用户补充

- 产品未来会规划 PC 版本，不仅是移动端 App，而是多端通用产品。
- 长期定位不应只限于“计划”，还包括：
  - 笔记
  - 想法记录
  - 资料整理
  - 个人知识与信息管理
- 长期目标是成为“个人助理型 App”。
- 当前名称“执行力”可能不再符合未来定位，需要保留更名空间。
- 用户现有笔记整理方式以大量手动分类文件夹为主，体验繁琐。
- 未来希望产品具备通过 AI 自动帮助整理、归类、沉淀内容的能力。
- 产品文档需要体现：
  - 当前版本以计划执行为核心切入。
  - 长期演进方向是多端个人助理与 AI 自动整理平台。

### 2026-04-02 第6轮检测用户补充

- 页面级详细需求需要固定格式，后续所有 PRD 保持一致。
- 每个页面都要按 UI 从上到下拆解，而不是只写抽象功能概述。
- 页面级描述需要直接对应视觉区块，说明每一块展示什么、为什么存在、能做什么操作。
- 交互流程不能笼统，复杂逻辑要单独拆开说明。
- 页面交互优先使用 Mermaid 流程图表达。
- `Now` 页尤其要写清：
  - `开始专注` 如何根据当前计划内容生成专注卡片或弹框。
  - `换一个` 如何切换到下一个推荐任务。
  - 专注弹框里的确认、取消、返回分别会发生什么。

## 当前闭环状态

- 已闭环：
  - PlanEditor 独立描述。
  - 原有核心模块与主流程覆盖。
  - 从当前版本范围中移除登录系统的必选依赖。
  - 增强整体 App 描述。
  - 将“离线可创建计划、本地存储、接口用于同步而非强依赖”的原则写入 PRD。
  - 将产品长期愿景扩展为多端个人助理，并为名称调整与 AI 自动整理能力预留空间。
  - 第 7 章页面级需求统一为固定模板。
  - 页面说明按 UI 从上到下拆解，并直接绑定页面素材。
  - 关键页面补充 Mermaid 流程图。
  - `Now` 页补充 `开始专注`、`换一个`、专注弹框的详细交互链路。
- 待继续观察：
  - 个别整体流程段落与页面级流程之间的表述是否还需要进一步收束到统一术语。
