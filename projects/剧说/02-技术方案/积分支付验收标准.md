# 剧说后端：积分与支付后端验收标准

> 适用范围：`T-B010-*` 积分账户 / 流水 / 冻结扣减退回，`T-B011-*` 支付订单 / 充值套餐 / 支付宝 / 微信支付 / Apple IAP / 回调到账。  
> 用途：分配后端开发任务、追踪完成进度、验收后端交付质量。  
> 进度口径：只写完代码不算完成，必须同时满足接口、数据、异常、幂等和测试凭据。

---

## 1. 后端总体验收口径

每个子任务建议按下面 5 个状态追踪：

| 状态 | 含义 |
|------|------|
| `未开始` | 未编码，或只有空文件 / 空接口 |
| `开发中` | 主逻辑编码中，尚未自测通过 |
| `待联调` | 本地单测/接口自测通过，可交给前端或 QA 联调 |
| `待修复` | 联调发现问题，需返工 |
| `已验收` | 接口、数据、异常、幂等、测试凭据均通过 |

单项任务达到 `已验收` 必须同时满足：

- 后端接口已实现，可通过 Swagger、Postman、curl 或集成测试调用。
- 请求参数、响应结构、错误码与接口文档一致。
- 数据表字段、索引、唯一约束、状态枚举和迁移脚本已提交。
- 涉及余额、订单、流水的操作必须在事务内完成。
- 重复请求、重复回调、并发点击不会重复扣费、重复冻结、重复到账。
- 关键异常有明确错误码或错误信息，不能只返回通用 500。
- 关键操作有日志，至少包含 `userId`、`orderNo/bizId`、操作类型、金额、处理结果。
- 有可复现的测试凭据：单元测试、集成测试、Postman/curl 记录、数据库结果截图任一即可。

后端提交时必须同步给验收人：

| 交付物 | 要求 |
|--------|------|
| 接口清单 | 路径、方法、鉴权要求、请求示例、响应示例 |
| 数据库变更 | 表结构、索引、唯一约束、迁移脚本 |
| 状态机说明 | 订单状态、账务操作状态、任务扣费状态 |
| 幂等说明 | 使用什么 key 防重复，重复请求返回什么 |
| 测试凭据 | 至少覆盖正常、异常、重复请求三类 |
| 部署配置 | 支付渠道、回调地址、沙箱/正式环境配置项 |

支付渠道范围：

| 渠道 | 后端验收重点 |
|------|--------------|
| 支付宝 | 订单创建、服务端签名、异步通知验签、重复通知幂等、退款/关闭预留 |
| 微信支付 | API v3 下单、商户证书/平台证书、回调验签解密、重复通知幂等、退款/关闭预留 |
| Apple IAP | 商品 ID 映射、客户端交易上报、服务端交易校验、App Store Server Notifications、退款/撤销同步 |

## 2. T-B010 积分账务验收标准

### T-B010-01 积分账户表、账户初始化、余额查询接口

| 验收项 | 标准 |
|--------|------|
| 数据表 | 存在积分账户表，至少包含 `user_id`、`available_points`、`frozen_points`、`version`、`created_at`、`updated_at` |
| 初始化 | 新用户首次登录或注册后自动创建积分账户 |
| 查询接口 | 登录用户可查询可用积分、冻结积分、累计充值/消耗或等价字段 |
| 权限 | 用户只能查询自己的积分账户 |
| 异常 | 未登录返回鉴权错误；账户不存在时自动初始化或返回明确错误 |
| 测试凭据 | 提供新用户登录后账户自动创建、余额查询成功、未登录失败的测试记录 |

完成判定：前端“我的/充值入口/生成前余额展示”可以稳定拿到余额。

### T-B010-02 积分流水表、收入/支出/冻结/退回流水记录

| 验收项 | 标准 |
|--------|------|
| 数据表 | 存在积分流水表，至少包含 `user_id`、`biz_type`、`biz_id`、`operation`、`direction`、`amount`、`balance_after`、`frozen_after` |
| 唯一约束 | 同一 `biz_type + biz_id + operation` 不能重复写入 |
| 流水类型 | 支持充值收入、生成冻结、生成扣减、失败退回 |
| 查询排序 | 流水按创建时间倒序分页返回 |
| 一致性 | 流水记录后的余额快照与账户余额一致 |
| 测试凭据 | 提供至少一组充值、冻结、扣减、退回后的流水截图或接口结果 |

完成判定：任意一次积分变化都能在流水中查到依据。

### T-B010-03 生成前积分预估、冻结积分、重复提交幂等

| 验收项 | 标准 |
|--------|------|
| 积分预估 | 根据视频时长、素材数量或当前业务规则返回预计消耗 |
| 余额校验 | 可用积分不足时禁止创建生成任务 |
| 冻结逻辑 | 创建生成任务时，可用积分减少，冻结积分增加 |
| 幂等 | 同一生成任务或同一幂等键重复提交，不重复冻结 |
| 并发 | 并发点击生成不会造成余额变负 |
| 测试凭据 | 提供余额不足、正常冻结、重复提交不重复冻结的测试记录 |

完成判定：用户点“生成”前后，积分冻结和任务创建能保持一致。

### T-B010-04 生成成功确认扣减、生成失败退回冻结积分

| 验收项 | 标准 |
|--------|------|
| 成功扣减 | 生成成功后冻结积分减少，并写入确认扣减流水 |
| 失败退回 | 生成失败后冻结积分减少，可用积分恢复，并写入退回流水 |
| 幂等 | 成功回调或失败回调重复到达，不重复扣减或重复退回 |
| 状态限制 | 未冻结的任务不能直接确认扣减；已扣减任务不能再次退回 |
| 联动 | 与生成任务状态、百度 VOD/Provider 回调或轮询结果联动 |
| 测试凭据 | 提供生成成功扣减、生成失败退回、重复回调幂等的测试记录 |

完成判定：生成链路无论成功失败，账户余额和流水都对得上。

### T-B010-05 积分明细接口、账本一致性校验、异常补偿脚本

| 验收项 | 标准 |
|--------|------|
| 明细接口 | 支持分页查询积分流水，能区分收入、支出、冻结、退回 |
| 筛选能力 | 至少支持分页；如时间范围或类型筛选已实现，需说明 |
| 一致性校验 | 能检查账户余额与流水累计是否存在差异，MVP 可用脚本或管理接口 |
| 补偿能力 | 对异常订单或异常任务有人工补偿方式，不能直接改数据库无记录 |
| 日志 | 关键账务操作有日志：用户、业务单号、操作、金额、前后余额 |
| 测试凭据 | 提供分页明细、异常校验或补偿流程说明 |

完成判定：出现账务问题时，能查得清、补得回、留得下记录。

## 3. T-B011 支付订单验收标准

### T-B011-01 充值套餐配置、套餐列表接口、套餐上下架字段

| 验收项 | 标准 |
|--------|------|
| 套餐表 | 套餐包含 `product_id`、名称、价格、赠送积分/权益、状态、排序 |
| 列表接口 | 前端可获取可售套餐列表 |
| 上下架 | 下架套餐不出现在用户端列表 |
| 金额单位 | 金额使用分或最小货币单位，避免浮点误差 |
| 异常 | 创建订单时选择不存在或下架套餐，应返回明确错误 |
| 测试凭据 | 提供套餐列表、下架不展示、下架套餐下单失败的测试记录 |

完成判定：前端充值页可以稳定展示真实套餐。

### T-B011-02 支付订单创建、订单号、金额校验、订单状态机

| 验收项 | 标准 |
|--------|------|
| 创建订单 | 登录用户选择套餐后可创建支付订单 |
| 订单号 | 订单号全局唯一，可用于回调、查询和日志定位 |
| 金额校验 | 订单金额以服务端套餐为准，不信任前端传入价格 |
| 状态机 | 至少支持待支付、支付中、已支付、失败、关闭或等价状态 |
| 幂等 | 同一 `Idempotency-Key` 重复创建订单返回同一业务结果 |
| 测试凭据 | 提供正常下单、重复下单幂等、非法套餐失败的测试记录 |

完成判定：创建订单不会出现错价、重复订单不可控、订单状态不明的问题。

### T-B011-03 支付渠道参数生成、客户端支付参数返回

| 验收项 | 标准 |
|--------|------|
| Provider 抽象 | 支付宝、微信支付、Apple IAP 封装在 Provider/Adapter 中，业务 Service 不写死某个渠道 |
| 支付参数 | 支付宝/微信创建订单后返回客户端需要的支付参数；Apple IAP 返回商品 ID、订单号和服务端校验所需关联字段 |
| 渠道记录 | 订单记录支付渠道、渠道订单号或预支付单号 |
| 异常 | 渠道下单失败时订单状态和错误信息可追踪 |
| 可替换性 | 从 mock 渠道切支付宝/微信/Apple 时，不需要改订单主流程 |
| 测试凭据 | 提供 mock 支付参数、支付宝沙箱、微信沙箱/测试商户、Apple Sandbox 任一对应记录 |

完成判定：前端拿到支付参数后可以拉起支付或完成 mock 支付。

### T-B011-04 支付回调接收、验签、重复通知幂等处理

| 验收项 | 标准 |
|--------|------|
| 回调入口 | 支持支付渠道回调接口，能接收原始回调内容 |
| 验签 | 真实渠道必须验签；mock 渠道需有等价校验或明确标记仅测试环境可用 |
| 原文保存 | 保存渠道回调原文、事件 ID、订单号、处理结果 |
| 幂等 | 同一渠道事件或同一订单重复回调，不重复发放积分 |
| 异常 | 验签失败、订单不存在、金额不一致、状态已终态均有明确处理 |
| 测试凭据 | 提供正常回调、重复回调、验签/金额失败的测试记录 |

完成判定：支付回调可以放心暴露给渠道，不会因为重复通知造成资损。

### T-B011-05 支付成功到账、积分入账流水、订单与账本绑定

| 验收项 | 标准 |
|--------|------|
| 到账逻辑 | 支付成功后调用积分账务服务发放积分 |
| 订单更新 | 订单状态更新为已支付，记录支付完成时间和渠道流水号 |
| 流水绑定 | 积分收入流水能关联支付订单号 |
| 事务一致性 | 订单成功和积分到账应在事务或补偿机制保护下保持一致 |
| 幂等 | 重复到账请求不重复加积分 |
| 测试凭据 | 提供支付成功后订单状态、账户余额、积分流水三方一致的测试记录 |

完成判定：用户付钱后积分能到账，订单和账本能互相追溯。

### T-B011-06 到账补偿、订单查询同步、异常订单处理

| 验收项 | 标准 |
|--------|------|
| 主动查询 | 支持按订单号查询支付状态，或提供 Provider 查询能力 |
| 补偿机制 | 回调丢失时可以通过查询或脚本补发积分 |
| 异常订单 | 金额不一致、用户不一致、订单关闭后回调等场景不直接到账 |
| 操作记录 | 人工补偿必须写日志和流水，不能只改余额 |
| 状态收敛 | 长时间待支付订单可关闭或标记超时 |
| 测试凭据 | 提供回调丢失补偿、异常订单拒绝到账、超时订单处理说明 |

完成判定：支付链路出异常时，有办法补偿且不会造成资损。

### T-B011-07 支付沙箱联调支持、日志字段、回归问题修复

| 验收项 | 标准 |
|--------|------|
| 环境配置 | 沙箱/正式配置隔离，不能混用密钥 |
| 日志字段 | 关键日志包含订单号、用户 ID、渠道、金额、事件 ID、处理结果 |
| 联调文档 | 提供沙箱测试账号、回调地址、测试套餐、测试步骤 |
| 回归用例 | 覆盖下单、支付成功、重复回调、金额错误、到账补偿 |
| 问题闭环 | QA 提出的 P0/P1 问题修复并回归通过 |
| 测试凭据 | 提供支付沙箱联调记录或 QA 验收记录 |

完成判定：支付功能可交给 QA 稳定回归，不再依赖开发口头说明。

## 4. 支付渠道后端验收标准

### 4.1 支付宝后端验收

| 验收项 | 标准 |
|--------|------|
| 配置 | `appId`、商户私钥、支付宝公钥、回调地址、网关地址按环境隔离 |
| 下单 | 后端按服务端套餐金额创建支付宝订单，不信任前端金额 |
| 签名 | 请求支付宝前由服务端完成签名 |
| 异步通知 | 支持支付宝异步通知入口，保存通知原文 |
| 验签 | 收到通知后必须使用支付宝公钥验签 |
| 金额校验 | 通知金额、订单号、商户号必须与本地订单一致 |
| 幂等 | 支付宝重复通知不重复发放积分 |
| 响应 | 通知处理成功后按支付宝要求返回成功响应；失败时记录原因 |
| 异常 | 订单不存在、金额不一致、验签失败、订单已关闭均不能到账 |
| 测试凭据 | 提供支付宝沙箱下单、成功通知、重复通知、金额异常或验签失败记录 |

完成判定：支付宝沙箱能完成“下单 -> 支付成功通知 -> 订单已支付 -> 积分到账 -> 重复通知不重复到账”。

### 4.2 微信支付后端验收

| 验收项 | 标准 |
|--------|------|
| 配置 | `mchId`、`appId`、API v3 key、商户证书、平台证书、回调地址按环境隔离 |
| 下单 | 后端按服务端套餐金额创建微信支付订单 |
| 签名 | 请求微信 API 时完成 API v3 签名 |
| 回调验签 | 收到微信支付通知后校验签名、时间戳、随机串和证书序列号 |
| 回调解密 | 对回调资源内容完成解密，拿到真实交易状态 |
| 金额校验 | 回调金额、订单号、商户号必须与本地订单一致 |
| 幂等 | 微信重复通知不重复发放积分 |
| 响应 | 通知处理成功后返回微信要求的成功结构 |
| 异常 | 验签失败、解密失败、金额不一致、订单已终态不能到账 |
| 测试凭据 | 提供微信测试下单、成功通知、重复通知、验签/解密失败记录 |

完成判定：微信支付能完成“下单 -> 支付成功通知 -> 订单已支付 -> 积分到账 -> 重复通知不重复到账”。

### 4.3 Apple IAP 后端验收

| 验收项 | 标准 |
|--------|------|
| 商品映射 | Apple `productId` 与本地套餐/权益一一映射，服务端不信任前端传入金额 |
| 订单关联 | 客户端发起购买前或购买后，能把本地订单号与 Apple 交易关联 |
| 交易上报 | 客户端购买完成后向后端上报 transaction 信息或 Apple 可校验凭据 |
| 服务端校验 | 后端向 Apple 校验交易真实性、商品 ID、环境、购买状态 |
| 防重复 | 同一 Apple transaction 只能发放一次权益 |
| 通知接收 | 支持 App Store Server Notifications，用于同步退款、撤销、续订、过期等事件 |
| 退款/撤销 | 收到退款或撤销事件后能标记订单和权益状态；点数型商品如已消费，需有人工处理策略 |
| 沙箱 | 支持 Apple Sandbox 测试账号和沙箱环境校验 |
| 异常 | 商品 ID 不匹配、交易已处理、环境不匹配、校验失败时不能到账 |
| 测试凭据 | 提供 Apple Sandbox 购买成功、重复上报、商品不匹配、退款/通知接收记录 |

完成判定：Apple IAP 能完成“购买成功 -> 服务端校验 -> 订单已支付 -> 权益到账 -> 重复交易不重复到账”，并能接收 Apple 服务端通知。

### 4.4 三渠道统一验收

| 验收项 | 标准 |
|--------|------|
| 统一订单表 | 支付宝、微信、Apple 都写入同一订单模型或统一订单视图 |
| 统一到账 | 三个渠道最终都通过同一个积分/权益发放服务，不各自直接改余额 |
| 统一幂等 | 三个渠道都有渠道事件唯一键和本地订单幂等控制 |
| 统一日志 | 三个渠道日志字段一致，便于按订单号排查 |
| 统一查询 | 后端可按订单号查询订单、渠道、支付状态、到账状态 |
| 统一补偿 | 回调丢失或通知失败时，有可追踪的补偿方式 |

完成判定：换支付渠道不会改变积分到账和订单状态主流程。
