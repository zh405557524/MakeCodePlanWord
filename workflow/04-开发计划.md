# 04 开发计划

目标：把一个版本拆成**可以各自独立执行和验收的功能模块**，每个模块一份计划；另有一份只管顺序和状态的总计划。执行者一次只读一个模块计划，不读整个版本的历史。**开工条件不具备时必须停下，不能猜。每个界面都必须有设计依据，缺的在写任务之前一次性告诉用户。**

> **设计依据**：Figma 节点，或设计稿 / 设计图文件（png、jpg、pdf 等）。两种都可以，但每个界面、每个状态必须有其中一种，开发时照着它做、做完对着它截图核对。用户明确指定"沿用某现有页面"时，把那个页面的截图存为设计图，也算设计依据。

> 分工（2026-11-26 定）：Claude 写计划，并把后端、前端的代码都写了；ChatGPT / Codex 负责实际运行：编译、跑测试、走验收路径。模块计划要写到"不需要猜"的程度，Codex 的检验计划同样。

## 产出

- `vX.Y.Z/04-开发计划/开发计划.md`：**总计划**。只管模块清单、依赖、状态、开工条件结果，不写任务细节。
- `vX.Y.Z/04-开发计划/模块/Mxx-模块名.md`：**模块计划**，每个功能模块一份。
- `vX.Y.Z/05-测试/测试.md` 的用例部分：按模块分组，和计划一起写（第 6 节）。
- `vX.Y.Z/04-开发计划/待执行/`、`待检验/`、`已执行/`：给 Codex 的检验、复检、修复计划（第 12 节）。

模板：工作台 `templates/version/04-开发计划/开发计划.md`（总计划）、`templates/version/04-开发计划/模块/模块计划.md`、`templates/version/04-开发计划/待执行/检验计划.md`。

## 输入（写计划前必须读）

1. `当前产品文档/` 相关模块 + 本版 `01-产品/requirements.md` 已确认增量；`requirements-list.md` 的 R / AC
2. `02-设计/设计计划.md`，以及本模块涉及的全部设计依据（Figma 节点，或设计稿 / 设计图文件）
3. `03-技术规划/技术方案.md`，以及 `api.md`、`data-model.md` 里本版改动的小节
4. 每个涉及仓库的 `AGENTS.md` 和它索引的相关规范
5. 相关的现有代码：要改的文件、可复用的组件和服务、相似功能的现有实现
6. 项目 `testing/risk-checklist.md` 中本版勾选的领域

## 1. 怎么拆模块

- **按用户能看到的功能区域拆。** 每个模块有一条能从头走到尾的用户路径，例如"创建视频流程""素材管理""视频剪辑与导出"。
- **模块不按前端 / 后端拆，也不按接口或文件拆；模块内部的任务分两组：后端任务、前端任务。** 先做后端、再做前端，各自只对接口文档负责；后端先做好，前端直接连它，不做假数据（见第 4 节 §6）。
- 被多个模块依赖的基础能力（登录、支付、资源上传）单独成模块，排在前面。
- **最后固定一个「统一联调」模块（M99）。** 它不写新功能：Codex 检验和复检做完、问题清单处理完以后，把各模块的验收路径从头到尾走一遍。**后端、前端的全量测试只在这里跑一次**（各模块的任务只测自己改到的部分）。
- **符合条件的版本，最前面加「打样」（M00）**，见第 2 节。
- 大小：一份模块计划不超过 300 行、任务不超过约 10 个；超过就再拆。
- 每个模块写清：对应哪些 R / AC、依赖哪些模块、不碰哪些模块、**会改哪些文件和目录**（用来判断能不能并行）。

## 2. 总计划写什么

只写这些：接口改动总览（整个版本）、基本信息（仓库路径、分支）、打样、模块清单表、执行顺序和并行安排、全局不改动范围、全局风险、问题清单、调整记录。

**接口改动总览（整个版本）**：放在最上面，由各模块计划的总览汇总而成，多一列“模块”。只看这张表，就能知道这一版在最上层改了什么。

**不写**：任务、文件路径、具体做法、测试通过数量、提交号清单、修复经过。这些在模块计划、git 提交和 `evidence/` 里。

**打样（M00）**：满足任意一条就必须做——新项目搭框架；工作量超过 1 天；链路很长（跨三个以上环节，或要接外部服务、模型、支付）；用了以前没用过的技术或做法。总计划里写清三样：走哪一条最窄的主链路（从界面点一下，经过接口、数据库、外部服务，结果回到界面）；要证明哪几件最没把握的事；不做什么（界面细节、异常处理、其余功能）。打样通过（Codex 实际运行、用户看过，见 `05` 第 3 节）才开始写模块；打样的代码留下来当骨架。不需要打样的，写一句“不打样”和原因。

**并行安排**：互不依赖、会改的文件和目录也不重叠的模块可以并行，在“执行顺序”里写明哪几个并行、各用哪个分支和工作区。公共文件在这里提前分好：迁移脚本的版本号、多语言文件的 key 前缀、路由表、`api.md` 的小节归谁写。并行期间接口不改。同一个代码仓库同时进行的任务最多 3 个（暂定）。做法见 `05` 第 8 节。

**问题清单**：开发和检验中没有当场解决的事都登记在这里，不只是修 3 次没解决的。每条写：哪个模块、类型、现象、证据、做过什么、判断的原因、属于后端 / 前端 / 接口文档 / 计划 / 需求、Codex 核实结论、处理结果。类型固定：自审遗留（Claude 审核 3 轮没解决或拿不准）、检验发现、计划漏写、需求没写到、没做、既有问题、外部条件。

模块清单表的取值固定：

| 列 | 允许的值 |
|---|---|
| 开工条件 | 就绪 / 阻塞：缺…… / 未检查 |
| 状态 | 草稿 / 已审核 / 执行中 / 阻塞 / 待检验 / 待验收 / 通过（日期） |
| 后端、前端 | 待开始 / 进行中 / 完成 / —（不涉及） |
| 自审 | 未开始 / 通过 / 有遗留（见问题清单） |
| 检验 | 未开始 / 通过 / 有问题（见问题清单） |
| 分支 | 分支名；并行时加工作区目录 |
| 等谁 | Claude / Codex / 用户 / — |

状态的意思：已审核 = 可以交给 Claude 写；待检验 = 代码写完、自审做完，等 Codex 检验；待验收 = 检验通过，等用户。**这几栏只写表里的词，其他说明写进“备注”栏、问题清单或模块计划**，否则进度页（`scripts/progress.py`）读不出来。**进度不手改，用 `scripts/set-status.py` 改**（`05` 第 11 节）。写模块计划和检验计划时，把这条命令连同项目名、版本、模块号填好，写在每组任务的最后（模板里已有位置），执行的 AI 照抄运行。它不一定会去读细则，但一定会读计划。

## 3. 开工条件检查（每个模块计划的第 1 节，必填）

写计划的人填写，**执行者开工前重新实际核对**（见 `05`）。七项：

| 条件 | 怎么算满足 |
|---|---|
| 产品 | 模块涉及的 R / AC 已经用户确认，没有"待定""暂不确定" |
| 设计 | 模块里**每一个界面、每一个状态**都有设计依据；§4 写出 Figma 节点 ID 或设计图文件路径；没有"待确认"行 |
| 技术契约 | 用到的接口、表、配置已在 `api.md`、`data-model.md` 定义；接口有样例（成功一份，每种失败各一份）。缺样例的回技术规划补，不在计划里自己编 |
| 外部条件 | 账号、Key、渠道、测试环境可用；写明怎么验证它可用 |
| 前置模块 | 依赖的模块代码已写完、自审已做。依赖的模块标“阻塞”时，本模块也标“阻塞”并跳过，先做下一个模块 |
| 工具 | 设计依据能实际打开（Figma 能连接并读取节点，或设计图文件存在且能查看）；仓库规范已读 |
| 测试基线 | 开工前把本模块相关的现有测试跑一遍（Claude 的环境跑不了就交给 Codex），失败名单存 `05-测试/evidence/基线/`。基线有失败的：先开一个模块把它修好，或者写明“带着这些失败开工”并由用户同意。不记基线，后面分不清是不是这次改坏的 |

结果：

- 全部满足 → 开工条件"就绪"。
- 任一不满足 → 模块状态改"阻塞"，写清**缺什么、需要谁提供**，**该模块不写代码**；不依赖缺失条件的其他模块照常进行。

**设计核对（重点，写任务之前完成）**

1. **先从需求列界面清单。** 按本模块全部 AC 和 §8 用户路径，列出用户会看到的每一个界面和状态：页面默认、加载、空、错误、无网络、无权限、弹框、底部弹层、提示（toast）、确认框、成功页。清单从需求推出来，**不是从设计稿里有什么推出来**，这样才能发现缺的。
2. **逐行找设计依据**：Figma 节点，或设计稿 / 设计图文件，写进 §4。
3. **缺的一次性通知用户。** 找不到依据的行，汇总成「设计缺失清单」，**在写任务之前**一次发给用户：缺哪个界面 / 状态、对应哪条 AC、影响哪些功能、建议（补稿，或沿用哪个现有页面）。不要零散地问，更不要等开发时再说。
4. **只接受两种答复**：用户补了 Figma 节点或设计图；用户明确回复"沿用某某现有页面"（原话写进 §4，并把该页面截图存为设计图）。不能用"参考类似页面""通用样式""先做个简单版"填空，那等于替用户做设计。
5. **§4 还有任何"待确认"行，本模块不能审核通过，不写任何代码。**

## 4. 模块计划的结构

模板见 `templates/version/04-开发计划/模块/模块计划.md`。各节要求：

### 接口改动总览（放在最上面，第 0 节之前，不编号）

只看这张表，就能知道这个模块在最上层改了什么。

表的上面先写一行：**本模块的范围**——后端是哪个目录，App 是哪个页面目录。不写这一行，无法判断什么算模块外。

表的列：#、类别、接口或位置、改动、改之前、改之后、影响到谁。填好的例子见 `参考/开发计划示例.md`。

类别固定六种，每种都要有交代；没有改动的可以合并成一行，写“无改动”：

1. **对外接口**：HTTP 接口的路径、请求和返回的字段、状态值、错误码。
2. **内部接口**：模块之间公开的方法——名称、参数、返回值、含义。
3. **接口约束**：接口的样子没变，但规矩变了——校验规则、取值范围、必填或可空、默认值、调用前要满足的条件、状态限制、会返回哪些失败。对外接口和内部接口的约束都算。
4. **模块外 Service**：改了不属于本模块的 Service、Store 或接口封装（公共的、别的模块的）。即使方法名和结果都没变也要列，并写清四件事：哪个类的哪个方法、为什么非改它不可、还有谁在用、对他们有没有影响。
5. **数据结构**：表结构，App 本机缓存和持久化数据的键与格式。
6. **流程由谁推进**：用户确认、系统自动、外部事件。

- “改动”一栏只能写：新增、修改、删除、约束变化、行为变化（接口不变）、内部改动（接口和行为都不变）、无改动。
- “改之前”“改之后”各用一句用户看得懂的话，不贴字段。
- 不属于上面六类、但需要占一行的内部改动，类别写“内部实现”。
- 第 4 类如果只是内部改动、对别人没有影响，列在表里即可；会让别人看到的结果发生变化的，按第 2 或第 3 类处理。
- 字段和接口卡片在 `api.md` 和技术方案里，§5 负责链接过去。**总览就是本模块唯一的接口变化清单**，必须和技术方案一致；总览以外的接口变化，执行时一律不做。
- §6 的每个任务都要写明对应总览的哪一行。对不上任何一行的任务不做；确实需要做，先补全总览并重新审核。

### 0. 基本信息
模块编号和名称、对应 R / AC、依赖模块、状态、审核日期、涉及的仓库（绝对路径）、工作分支、执行者、**会改的文件和目录**（按仓库列到目录或文件；和别的模块有重叠就不能并行）。

### 1. 开工条件
第 3 节的七项，每项写结果和依据。

### 2. 本次已读规范（必填，缺这一节不予审核）

| 仓库 | 规范文件 | 和本模块相关的关键条款 |
|---|---|---|
| Solfeggio | AGENTS.md | 页面放 `lib/pages/{feature}/`，view / controller / index 三件套 |
| Solfeggio | .cursor/rules/01-conventions.mdc | 禁止在 View 中直接调 API |

关键条款要具体到"会影响本模块怎么写"的那几条。只写文件名不算读过。

### 3. 现状摘要
- 和本模块相关的现有代码在哪：文件路径 + 一句话说明它现在做什么。
- 可以复用的组件、服务、工具方法：写出类名或函数名。
- 相似功能的参考实现：写出文件路径，要求执行者照着写。

### 4. 界面与设计依据

| 界面 / 状态 | 设计依据（Figma 节点或设计图文件） | 对照用设计图 | 关联 AC | 说明（动态内容、业务文案来源） |
|---|---|---|---|---|
| 作品列表 · 默认 | Figma 12:345 | design-assets/projects-default.png | AC-09-01 | 卡片文案来自作品数据 |
| 作品列表 · 空 | 设计图 design-assets/projects-empty.png | 同左 | AC-09-02 | |
| 作品列表 · 加载失败 | 沿用通用错误页 | design-assets/common-error.png（现有页面截图） | AC-09-03 | 用户原话："沿用通用错误页"（10-21） |
| 剧集删除 · 确认框 | 待确认 | | AC-09-05 | 已列入设计缺失清单，等用户回复；本模块不能审核通过 |

界面清单从 AC 和 §8 推出，每个状态各占一行，不能合并成"同上"。"对照用设计图"是开发和截图核对时要照着的那张图：Figma 的写导出图路径，设计图文件写"同左"。**有"待确认"行，本模块不能审核通过。**

### 5. 契约
本模块用到的接口、表、配置，链接到 `api.md`、`data-model.md`、技术方案的对应小节。**不在计划里重新定义字段。** 发现契约不对或不够：先改技术规划，再写计划。

**AC 对照表**：本模块的每条 AC 占一行，写它由哪几个任务实现、在 §8 验收路径的第几步验证。一条 AC 里有几件事的（例如“入库、导入时都带上别名”），每件事都要有对应的任务。对不上任务的 AC，写明原因（不做 / 放到哪个模块）。审核计划时逐行看这张表，它是用来查漏写的。

### 6. 任务列表
任务分两组，先后端、再前端。一个任务 = 一个能单独验证的功能点，只属于一个端。

- **后端任务（B-xx）**：只改后端仓库。验证用接口测试：按 `api.md` 的样例发请求，返回与样例一致，数据库里的数据符合预期。**测试命令只写本任务改到的模块**（`./gradlew test --tests '*某某Test*'`），不写全量的 `./gradlew test`、`./gradlew build`；全量测试只写在统一联调（M99）里。
- **前端任务（F-xx）**：只改 App（或网页端）仓库。本模块的后端任务已经做完，前端直接连本机后端，**不做假数据**。每个界面和状态照 §4 的设计依据做。

任务的写法见模板 §6.1、6.2；填好的后端任务例子见 `参考/开发计划示例.md`。前端任务格式和后端任务相同：文件只列前端仓库的；“具体做法”写明复用哪些现有组件；“验证”写界面核对（真实运行的 App，各状态与 §4 的对照用设计图同视口并排截图）。

**验证由谁做**：Claude 写代码时，自己的环境能运行的就运行；不能运行的，在“结果”里写明“没运行”，不能写成通过。任务里写的验证命令、接口核对、界面核对，最终都由 Codex 在检验里实际做一遍（`05` 第 9 节）。

**一个任务只列一个端的文件。** 只改任务里列出的文件；计划没列的另一端文件要改时，先说明改哪个文件、为什么，记进任务“结果”和接口改动总览（见 `05` 第 5 节）。

**模块的最后是自己审核**（不单独编号）：两组任务都做完后，Claude 对着固定的四样审核，最多 3 轮，记录写在模块计划 §11（见 `05` 第 6 节）。

### 7. 不改动范围
明确列出本模块不能碰的目录、文件、接口、配置、其他模块的界面，以及本模块必须保持不变的接口。

### 8. 模块验收路径
用户视角的步骤清单，例如"打开 App → 点创建 → 选现成剧本 → 粘贴 → 下一步 →……"。每步写预期结果，标注对照 §4 哪一行的设计图，并标明这一步由谁推进（用户确认 / 系统自动 / 外部事件），和产品需求一致。每一步出现的界面都必须在 §4 里。Codex 检验时，在连着真实后端的 App 里按步骤走一遍，每步截图存 `05-测试/evidence/{模块}/`。**步骤必须覆盖本模块全部 AC。**

### 9. 风险与回滚
引用技术方案的风险、兼容与上线顺序；补上执行层面的：迁移能否回退、开关怎么关。

### 10. 调整记录
计划审核后的任何修改追加一行：日期、改了什么、原因。用户对缺失设计稿的原话也记在这里。

### 11. 审核记录
Claude 写完本模块后自己审核的记录：第几轮、查出了什么、改了没有。3 轮后没解决的和拿不准的，同时登记到总计划的问题清单（类型“自审遗留”）。

## 5. 任务粒度

- 一个任务的改动能在一次审查中看完（一般不超过 10 个文件）。
- 每个任务完成后，代码能编译、测试能通过，不留半成品。
- 一个任务只对应一个功能点；"顺便重构"单独成任务，并且要用户同意。

## 6. 测试用例和计划一起写

写计划的同时，在 `05-测试/测试.md` 按模块分组写好本版新增用例（规则见 `06-测试.md`）：

- 每条验收标准（AC）至少对应一条用例。
- 每个任务的"验证"里写出它负责的用例 ID。
- 能自动化的由执行者在任务里实现；不能自动化的（真机、真实商店、实体设备）标为人工用例。

## 7. 写给执行者的硬要求

计划会直接交给执行 AI，所以：

- **不写模糊词**："按需""酌情""适当""优化一下""参考现有实现"都不允许单独出现，必须写出具体文件、具体做法。
- **写全路径**：文件写仓库内完整路径；跨仓库的写清是哪个仓库。**交给 Codex 的计划里，提到的每一份文档（模块计划、总计划、`api.md`、测试文档、设计图目录）和每个仓库都写绝对路径**，例如 `/Users/soul/work/MakeCodePlanWord/projects/{项目名}/vX.Y.Z/04-开发计划/模块/M01-xx.md`。Codex 不知道文档在哪，只写文件名它找不到。把计划交给用户时，也给出这份计划自己的绝对路径。
- **写出名字**：新增的类、方法、字段、路由、多语言 key 都给出名字。
- **写出复用对象**：已有的组件、工具方法、服务，写出名字并要求复用，不许重写。
- **写出验证命令和界面核对方式**。
- **给数据例子**：涉及数据格式的给出示例值。
- **写出停止条件**：模块计划开头写明"遇到计划没写到的情况、设计稿缺失、产品规则不明确、外部条件缺失时，停下来报告，不要自行扩展或猜测"。

## 8. 保持文件短

- 总计划不超过约 150 行（不含接口改动总览和问题清单）；模块计划不超过 300 行。用 `scripts/check-plan.py` 检查。
- 计划里**不记录**测试通过数量、提交号清单、修复经过、"本轮完成"这类流水。提交号只在任务"结果"里写一个；过程在 git 提交和 `evidence/` 里。
- 任务"结果"最多 5 行：做了什么、提交号、没运行的验证、证据路径。更长的说明写进检验计划的交付报告或问题清单。
- 状态只用本规则定义的词。模块：草稿 / 已审核 / 执行中 / 阻塞 / 待检验 / 待验收 / 通过。任务：待开始 / 进行中 / 完成 / 阻塞。不再并行使用"开发检测""整项验收"等口径；上线前的测试阶段另见 `06`。

## 9. 小改动的简化写法

改动小（一两个文件、半天以内）时，可以只有一个模块，模块计划只要：接口改动总览、开工条件、已读规范、界面依据（有界面时）、文件清单和做法、不改动范围、验证和用例、模块验收路径。**接口改动总览、开工条件和模块验收路径一项都不能省。** 只涉及一个端的小改动，只写那一端的任务；两端都涉及时，仍然分后端、前端两组。小改动不用打样，但写完仍然要自己审核、交 Codex 检验。

## 10. 计划审核后的调整

**产品规则变化时，先改 `01-产品/requirements.md`（以及设计、技术文档），再改计划；不在计划或对话里直接改产品规则。**

| 受影响的任务状态 | 怎么改 |
|---|---|
| 待开始 | 直接修改任务内容 |
| 进行中 | 修改任务内容，并在"结果"里注明"做到一半时计划调整：……" |
| 完成 | **不改旧任务**，新增一个任务："B-09 调整：R-03 改为……（替代 B-03 的第 2 步）"，编号沿用所在的任务组 |

每次调整都在模块计划 §10 追加一行，涉及模块范围或顺序时同步更新总计划。改动大到推翻已审核的方案时，把模块状态改回"草稿"，重新审核。

## 12. 给 Codex 的计划放在哪

`04-开发计划/` 下三个文件夹，按“现在该谁动”分：

| 文件夹 | 放什么 | 谁动 |
|---|---|---|
| `待执行/` | 写好了、还没交给 Codex 的检验、复检、修复、联调计划 | 用户把它交给 Codex |
| `待检验/` | Codex 做完并填了结果的计划 | Claude 和用户看结果 |
| `已执行/` | 结果看过、问题已经登记或处理完的计划 | 不用管 |

- 文件名用类型开头：`检验-`、`复检-`、`修复-`、`联调-`，后面写范围，例如 `检验-M01至M06.md`。
- 检验计划照模板 `templates/version/04-开发计划/待执行/检验计划.md` 写。Codex 理解力有限，步骤、命令、只能改哪些文件、什么时候停，都要写全。文档和仓库一律写绝对路径（第 7 节）。
- 模块计划、总计划不放进这三个文件夹。
