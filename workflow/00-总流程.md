# 00 总流程（v2）

> 适用场景：独立开发者 + AI 编码。可以是 Claude 出计划和审查、ChatGPT/Codex 执行，也可以是一个 AI 全程。
> 本文是流程总纲；`workflow/01–10` 是每一步的细则，进入哪一步再读哪一份。
> 旧版 01–19 阶段规则已移到 `legacy/v1/`，只供追溯，不再作为执行依据。

---

## 1. 两个核心概念

| 概念 | 是什么 | 放在哪 |
|---|---|---|
| **基线** | 线上产品"现在是什么样"。按功能模块拆，不按版本拆，永远只有一份 | `doc/product/`、`doc/tech/`、`doc/testing/` |
| **版本** | 这一版"要改什么"。开发中随时可以改；发布时合并回基线、打 git tag、冻结 | `doc/versions/vX.Y.Z/` |

四条铁律：

1. **基线 = 线上版本的真相。** 没发布的改动只写在版本文件夹里，不提前写进基线。修线上 bug 时，看基线就知道线上应该是什么行为。
2. **归档 = git tag。** 不再复制文件到 `archive/`。文档在工作台仓库，发布时在工作台打 `{appCode}-vX.Y.Z` 标签（代码仓库另打 `vX.Y.Z`）。要看旧版本：在工作台执行 `git show solfeggio-v2.1.0:projects/钢琴视奏/doc/product/xxx.md`。
3. **状态写在版本文件里，过程写在 git 提交里。** 不再维护流水账式的 `workflow.md`、`change-plan.md`、`change-log.md`。
4. **新项目和迭代走同一套流程。** 新项目就是 `v1.0.0`，`changes.md` 里写全量需求。

## 2. 文档放在哪

**工作区和代码分开。**

- **项目文档放工作台 `projects/{项目名}/doc/`**（称为文档目录、docRoot）：产品、技术、测试、版本都在这里。
- **代码仓库只放代码和编码规范**：仓库根 `AGENTS.md` + 规范目录（如 `.cursor/rules/`）。`AGENTS.md` 里写明文档目录的绝对路径，AI 在仓库里写代码时按这个路径去读计划和基线。
- **后端多个 App 共用时**：后端仓库的 `AGENTS.md` 按 App 列出各自的文档目录。某个 App 的接口契约写在这个 App 的文档目录 `tech/api.md`。
- 每个项目的文档目录登记在工作台 `workspace-registry.json` 的 `docRoot` 字段。
- **本文和所有细则、模板里的 `doc/` 都指文档目录**，不是代码仓库里的 `doc/` 文件夹。

文档目录的结构：

```
doc/
├── README.md             当前线上版本、开发中版本、文档地图（一页）
├── product/              基线需求，按模块拆（00-overview.md + 每个模块一份）
├── tech/                 基线技术：architecture.md、api.md、data-model.md（前后端共用）
├── design/               设计来源索引（Figma 链接、外部稿、AI 参考图、切图位置）
├── testing/
│   ├── regression.md     长期维护的回归用例集，按模块，标出冒烟用例
│   └── risk-checklist.md 高风险领域必测清单
├── backlog.md            想法池
└── versions/
    ├── v2.0.1/           已发布，冻结
    └── v2.1.0/           开发中：scope.md / changes.md / plan.md / test.md / release.md
```

## 3. 版本生命周期

```
① 版本规划 scope.md → ② 需求变更 changes.md → ③ 设计（可选）
→ ④ 开发计划 plan.md（同时在 test.md 写好用例）→ 【人工审核计划】
→ ⑤ 开发执行（逐任务实现 + 自测）→ ⑥ 测试验收（test.md 记录结果）
→ ⑦ 发布 release.md → 合并回基线 + 打 tag + 冻结版本文件夹
```

| 步骤 | 细则 | 产物 | 需要用户确认 |
|---|---|---|---|
| ① 版本规划 | `01-版本规划.md` | `scope.md` | ✅ 确认范围 |
| ② 需求变更 | `02-需求变更.md` | `changes.md` | 关闭"待确认决策"中的高风险项 |
| ③ 设计 | `03-设计.md` | `scope.md` 设计来源表、`doc/design/` | 只有"自己出稿"时确认稿子 |
| ④ 开发计划 | `04-开发计划.md` | `plan.md` + `test.md` 用例 | ✅ 审核计划 |
| ⑤ 开发执行 | `05-开发执行.md` | 代码 + `plan.md` 任务状态 | 遇到计划外情况才问 |
| ⑥ 测试验收 | `06-测试验收.md` | `test.md` 执行结果 | 查看结果、决定遗留问题 |
| ⑦ 发布 | `07-发布.md` | `release.md`、基线更新、tag | ✅ 确认发布、审核基线合并 |

- 线上问题走 `08-线上问题.md`：开 patch 版本，只写一页 `fix.md`。
- 新项目先看 `09-新项目初始化.md`；v1 旧工作区的项目先看 `10-旧项目迁移.md`。
- 小改动可以把 ②③④ 写得很短（几行），但不能跳过 ④ 的计划审核。

## 4. 版本号与版本状态

**版本号 = 商店版本号**（`major.minor.patch`），构建号另计。

| 升哪一位 | 什么时候 |
|---|---|
| minor | 有新功能、付费或权益变化、数据结构变化 |
| patch | 只修 bug、改文案、小调整，不新增功能 |
| major | 产品大改、推倒重来 |

- 单个改动没有自己的版本号，不再给每个改动分配 CHG 编号和版本号。
- 版本状态只有四个，写在 `scope.md`（patch 写在 `fix.md`）顶部，并同步到 `doc/README.md`：
  `规划中 → 开发中 → 测试中 → 已发布`
- "本地完成""未发布但已验收"都不是版本状态。任务完成情况写在 `plan.md` 的任务上；版本只有上线了才算"已发布"。

## 5. 改动怎么处理（决策表）

| 情况 | 例子 | 处理 |
|---|---|---|
| 版本未发布，发现需求有问题 | 弹框文案、某条规则细节要改 | 直接改 `changes.md` 对应条目，在条目的"调整记录"追加一行（日期 + 改了什么）；同步 `plan.md` 中受影响的任务（规则见 `04` 第 7 节） |
| 版本未发布，想加小功能 | 加收藏 | 写进 `changes.md`，并在 `scope.md`「范围变更」登记一行 |
| 版本未发布，想加大功能 | 新的练习模式 | 写进 `backlog.md`，留给下个版本 |
| 版本未发布，不做某功能了 | 去掉一个页面 | `changes.md` 中把条目标为"取消"并写原因；`scope.md` 范围变更登记；已经写了代码的，在 `plan.md` 加一个"移除"任务 |
| 已发布，线上 bug | 订单币种不对 | 开 patch 版本，按 `08-线上问题.md` 处理 |
| 已发布，要做新功能 | 下一个大版本 | 新开版本文件夹，从 `backlog.md` 挑范围 |
| 线上要修 bug，同时下个版本在开发 | | patch 从上一个发布 tag 拉分支修，发布后合回主分支（见 `08` 第 4 节） |

**大小怎么判断：** AI 一天内能做完、不改数据结构、不影响付费和权益 → 小；否则 → 大。拿不准就问用户。

## 6. AI 每次开始工作前必做

1. **确认项目和文档位置。** 在代码仓库里：读仓库根 `AGENTS.md`，里面写着文档目录的路径。在工作台里：查 `workspace-registry.json` 得到 `docRoot`。
2. **读 `doc/README.md`**，知道线上版本和开发中版本。开发中版本可能同时有两个（一个 patch 修线上问题，一个功能版本在规划或开发）：用户没说是哪个时先问，不要把一个版本的改动写进另一个版本。
3. **读开发中版本的 `scope.md`**，再根据各文件是否存在、状态字段判断现在处于哪一步：
   - `scope.md` 状态还是"规划中" → ①
   - `changes.md` 还是空模板，或有未关闭的高风险待确认 → ②
   - `plan.md` 还是空模板，或状态不是"已审核" → ④
   - `plan.md` 已审核、还有未完成任务 → ⑤
   - 任务全部完成、`test.md` 未执行完 → ⑥
   - 测试通过 → ⑦
4. **要写代码时**，先读代码仓库的 `AGENTS.md` 和它索引的相关规范（见 `05`）。
5. **只读当前步骤需要的文件**，不要通读整个 `doc/`，也不要一次读完 `workflow/` 下所有文件。

---

## 7. 不要做的事

- 不要为一个小改动新建一套流程文档；在当前版本的 `changes.md` / `plan.md` 里加一条就够了。
- 不要把执行过程（命令输出、尝试过程、阶段汇报）写进文档。测试证据放 `test.md` 的证据链接，过程放 git 提交信息。
- 不要在基线文档里写"v2.1 新增""原来是……"之类的版本痕迹；版本差异看 git。
- 不要跳过计划审核直接改代码。线上紧急修复也要先有一页 `fix.md`。
- 不要把旧工作区的 `archive/`、`change-plan.md`、`workflow.md` 当作编码依据。
