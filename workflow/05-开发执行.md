# 05 开发执行

目标：按已审核的 `plan.md` 逐个任务实现，每个任务都验证通过、状态写回计划。

## 1. 开始前（每次新会话都要做）

1. **读代码仓库根目录的 `AGENTS.md`**（Codex、Cursor 会自动加载；Claude Code 通过 `CLAUDE.md` 导入）。里面写着项目文档目录的路径（在工作台 `projects/{项目名}/doc/`，下文的 `doc/` 都指它）。
2. **按 `AGENTS.md` 的「规范索引」读本次任务相关的规范**（仓库规范目录，如 `.cursor/rules/`）。UI 任务读 UI 规范，修 bug 读 bug 修复规范，以此类推。
3. 读文档目录的 `README.md` 找到开发中版本，读该版本的 `plan.md`（线上问题读 `fix.md`）。
4. 确认 `plan.md` 状态是"已审核"或"执行中"。**不是的话不写业务代码**，只可以读代码、回答问题、帮忙写计划。
5. 跨仓库任务：进入另一个仓库前，先读那个仓库的 `AGENTS.md`。

> 工作台里的 `templates/repo-rules/` 只是新项目的模板。编码时以**代码仓库里的规范**为准。

## 2. 每个任务的循环

1. 把任务状态改为"进行中"。
2. 按"具体做法"实现。只改"仓库与文件"里列出的文件；要动其他文件，先停下来说明原因。
3. 跑任务里写的验证命令，加上仓库 `AGENTS.md` 规定的通用验证命令（例如 `flutter analyze`、`./gradlew build`）。
4. 验证通过后，把任务状态改为"完成"，在"结果"里写：做了什么、提交号（如果提交了）、和计划不一致的地方。
5. 建议每个任务提交一次，提交信息带版本号和任务号，例如 `v2.1.0 T-03: 订单保存商店实际币种`。是否由 AI 提交，按用户习惯。

## 3. 遇到计划外情况

以下情况**停下来报告**，不要自己扩展范围：

- 计划写的文件或方法不存在、和描述不一致
- 需要修改"不改动范围"里的内容
- 实现中发现需求有漏洞或矛盾
- 验证失败，且原因不在本任务范围内
- 需要新增依赖、改数据库结构、改配置，而计划没写

报告内容：哪个任务、发现了什么、建议怎么做、需要谁决定。用户决定后，由写计划的人更新 `plan.md`（按 `04` 第 7 节），再继续执行。

## 4. 执行中可以改哪些文档

| 文档 | 能不能改 |
|---|---|
| `plan.md` | 只改任务状态和"结果"；改任务内容要按 `04` 第 7 节 |
| `test.md` | 填写自动化测试的执行结果 |
| `doc/product/`、`doc/tech/` | **不改**。基线在发布时统一合并 |
| 仓库 `AGENTS.md` 的「常见坑」 | 发现值得记录的项目经验，可以补一条 |

## 5. 全部任务完成后

1. 跑一遍全量自动化测试和静态检查。
2. 把 `plan.md` 状态改为"完成"。
3. 给出执行报告：完成的任务、验证结果、偏离计划的地方、遗留问题。
4. 进入 `06-测试验收.md`。

## 6. 审查执行结果（写计划的人做）

执行者是另一个 AI 时，写计划的人逐个任务审查：

- 改动是否只在计划列出的文件内
- 是否遵守了「已读规范」中列出的条款
- 是否复用了计划指定的组件，有没有重复造轮子
- 测试是否真的覆盖了对应的 AC，而不是只测了正常路径
- 有没有"顺手"的改动

发现问题就在对应任务的"结果"里记下，并新增修正任务或退回重做。
