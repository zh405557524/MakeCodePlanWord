# 09 线上问题（patch 版本 / 修复单）

目标：线上 bug 用最轻的流程修好，并且保证同类问题下次能在测试阶段被发现。

patch 版本不走八个阶段的全套文件，只有一份 `vX.Y.Z/修复单.md`（证据放 `vX.Y.Z/evidence/`）。修复单里依次写产品现象、技术原因、修复方案、测试、上线和归档，相当于八个阶段压缩成一页。

## 1. 先分类

| 问题类型 | 处理 |
|---|---|
| 线上 bug：行为和 `当前产品文档/` 不一致 | 开 patch（本文） |
| 产品文档本身写错了、规则需要改 | 小的开 patch，并在修复单「文档同步」写明要改哪里；大的进下个功能版本 |
| 体验问题、新需求 | 写进 `backlog.md` |
| 崩溃、资金错误、数据损坏 | 开 patch，优先处理；必要时先暂停放量或关闭相关开关 |

## 2. patch 流程

1. 创建：
   ```bash
   /Users/soul/work/MakeCodePlanWord/scripts/new-version.sh /Users/soul/work/MakeCodePlanWord/projects/{项目名} vX.Y.Z --patch
   ```
   例如线上是 v2.1.0，就开 v2.1.1。这个 patch 已经存在时，在修复单里加一节。
2. 写修复单（模板 `templates/patch/修复单.md`）。一个 patch 可以修多个问题，每个问题一节（F-01、F-02……）：
   - 现象：用户看到什么、影响多少用户、从哪个版本开始
   - 复现：步骤、环境（地区、币种、设备、账号类型）
   - 原因：定位到代码或配置的具体位置
   - 修复方案：改哪些文件、怎么改（格式同开发计划的任务，必须有"已读规范"）
   - 数据修复：已经产生的错误数据要不要修、怎么修（脚本、范围、备份）
   - 验证：自动化测试 + 数据链路检查 + 回归范围
   - **防再发**：补进 `testing/regression.md` 的用例、补进 `testing/risk-checklist.md` 的维度
   - **文档同步**：这个修复改变了产品行为或接口时，写清楚 `当前产品文档/`、`api.md`、`data-model.md` 的哪个文件哪一节要怎么改
3. 用户确认修复方案（紧急时可以和上线确认合并为一次）。确认前不改代码。
4. 按 `05-开发.md` 修复、验证。
5. 按 `07-上线.md` 上线，上线记录写在修复单里。
6. 按第 5 节归档。

## 3. "防再发"必须做

每个线上 bug 修完都要回答：**为什么测试阶段没发现？**

- 缺用例 → 在 `regression.md` 补一条能复现它的用例。
- 缺维度（例如只用一个地区账号测过）→ 在 `risk-checklist.md` 加一条检查维度，写明来源。
- 用例只查了界面没查数据 → 在用例里补"预期（数据）"，并检查同模块其他用例有没有同样的问题。

## 4. 和开发中的功能版本同时进行

**文档**：已归档的版本文件夹冻结，patch 不改它。修复单「文档同步」里的改动：

- patch 归档时直接改 `当前产品文档/`（它描述线上功能，patch 上线就是线上）。
- 复核每个开发中版本与更新后基线的关系：冲突和受影响增量写进 requirements.md，requirements-list.md 记录来源“patch vX.Y.Z F-xx”，同步评审和复检；复制过来的 `03-技术规划/` 同步修复，未改产品内容只更新基线引用。

开新版本时如果有还没归档的 patch，`new-version.sh` 会提示。

**代码**：主分支上已经有未上线的新功能时：

1. 从上一个上线 tag 拉分支：`git switch -c hotfix/vX.Y.Z vX.Y.(Z-1)`。
2. 在 hotfix 分支上修复、测试、出包、上线，并在这个分支上打 tag。
3. 把 hotfix 分支合回主分支。如果开发中版本也改了同一块代码，在它的开发计划加一个任务处理冲突。

后端是多 App 共用的，修复前先确认改动不影响其他 App；影响的话在修复单写清楚，并跑其他 App 的相关测试。

## 5. patch 归档

- 用例合并进 `testing/regression.md`，维度合并进 `testing/risk-checklist.md`
- 「文档同步」已经写进 `当前产品文档/` 和所有开发中的版本
- 修复单状态改为"已归档"
- 项目 `README.md`：线上版本改为这个 patch；版本列表加一行
- 打 tag：工作台 `{appCode}-vX.Y.Z`，App 仓库 `vX.Y.Z`；hotfix 分支已合回主分支

## 6. 只改后端、不发 App 的修复

App 版本号不变，但修复已经上线：

- 记在下一个 patch 的修复单里（还没有就新开一个），这一节写明"仅后端，已于 YYYY-MM-DD 上线"，以及后端版本号和提交号。
- "防再发"照常做，用例和风险维度可以马上合并进 `testing/`，不用等 App 发版。
- 接口或产品行为变了的，马上按「文档同步」改 `当前产品文档/`，并写进开发中版本的文档。
- 后端仓库打 tag：`{appCode}-backend-{后端版本号}`，例如 `solfeggio-backend-5.0.0`。
