# 10-校验与失败处理

> 什么时候读：新增或修改校验、断言、异常处理、重试、状态判断。
> 判断是为了保护用户和钱，不是为了证明代码自己没写错。每写一个“不满足就报错”，先回答：它挡的是什么真实风险？拦下以后用户怎么走出去？

## 一、只为底线而拦截

只有下面六类可以“不满足就拒绝”。不在清单里的判断，删掉，或改成警告日志后继续。

1. **钱**：冻结、结算、退回各只发生一次；付费能力只调用一次。
2. **权限**：只能读写本人、本 App 的数据。
3. **用户内容**：不覆盖用户手动修改过的内容。
4. **审核与合规**：没通过审核的内容不展示、不交付。
5. **外部输入**：请求参数、上传的文件、第三方回调、模型返回的内容是否可用。
6. **流程状态**：用户的操作必须从合法的状态发起。

项目可以调整这张清单，但它必须是写下来的、有限的。

## 二、不要写的判断

- **不复核系统自己刚写的数据。** 同一个流程里前一步写入、后一步读出的数据，不再逐字段比较“是否一致”。
- **幂等用“做过就返回”。** 不用“状态不是某个值就报错”。重复请求到达时状态已经变了是正常现象。
- **冗余字段要有回退。** 快照、缓存、检查点里的字段只是副本，读不到时回到源头取，不直接走进错误分支。
- **查询不因一条脏数据整体失败。** 某条记录对不上，降级为空并打警告日志，其余照常返回。
- **外部和模型的输出，能纠正的纠正。** 多余的空白、标点、序号写法、数值略有出入，由程序修正并留日志；内容确实不可用才判失败。

## 三、失败了怎么处理

| 类别 | 例子 | 处理 |
|---|---|---|
| 用户能改的 | 内容不合规、参数不完整 | 立即返回，告诉用户是哪里、怎么改 |
| 临时故障 | 网络超时、服务繁忙 | 退避重试，必须有次数或时间上限 |
| 程序问题 | 数据对不上、出现了不该有的状态 | 立即失败，打错误日志；用户看到“系统处理异常”；付费任务退回 |

- 不把不认识的异常一律当临时故障去重试。
- 每一次拒绝都要有出路：提示里说明下一步能做什么，不能出现死路。
- 给用户的话用用户见过的词；技术原因写进日志，不拼进用户文案。
- 校验不通过要打日志，带上任务或对象编号、哪一步、原因。
