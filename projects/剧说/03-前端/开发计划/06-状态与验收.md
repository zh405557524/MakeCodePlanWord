## 1. 功能定位与边界

本模块负责补齐全 App 的状态体系、异常处理和最终验收口径，确保前面模块不是只完成静态页面，而是具备可用的 loading、empty、error、disabled、submitting、success、not_found 等状态。

本模块包含：

- 全局状态组件。
- 页面状态枚举和基类约定。
- 表单提交状态。
- API mock 异常开关。
- 登录、创作、作品、商业化、设置、反馈的状态验收清单。
- `flutter analyze` 和基础手动验收路径。

本模块不包含：

- 真实后端接口联调。
- 自动化测试框架的完整搭建。
- 性能压测、崩溃监控、APM。
- 商店上架 QA；这些属于后续联调测试和构建上架阶段。

## 4. 视觉参考与设计稿分析

状态类 UI 的设计来源分两类：

| 状态 | 来源 | 说明 |
|------|------|------|
| 作品空态 | Figma `1:1542` / `4` | 可作为全局空态风格参考 |
| 权益不足 | Figma `1:951` / `2` | 全局提示弹窗参考 |
| 积分确认 | Figma `1:1219` / `3` | 确认类弹窗参考 |
| 删除确认 | Figma `1:19` / `20` | 危险操作二次确认参考 |
| 表单错误 / 网络错误 | PRD 状态规则 | Figma 未展开，按项目深色视觉补齐 |

全局状态应保持深色视觉体系，按钮和高亮与现有 Figma 一致。空态、错误态不能占用过多首屏空间；表单错误需要靠近对应输入项或使用 toast，不要只在控制台输出。

## 6. 业务内容与数据流

### 6.1 页面状态流

```text

Controller.load()
  -> state = loading
  -> Api / MockService
  -> empty ? state = empty
  -> error ? state = error
  -> success ? state = success
  -> View update

```

### 6.2 提交状态流

```text

点击提交
  -> validate
  -> submitting = true
  -> Api / MockService
  -> success toast / route
  -> fail toast / keep form data
  -> submitting = false

```

提交状态适用于：

- 登录。
- 获取验证码。
- 立即生成。
- 积分确认。
- 会员充值。
- 积分充值。
- 意见反馈。
- 退出登录 / 注销账号确认。

### 6.3 Mock 异常策略

`MockService` 至少支持：

- 默认成功。
- 返回空列表。
- 抛出网络错误。
- 抛出业务错误。
- 延迟响应。

页面验收时需要能切换这些状态，确认 UI 不崩溃、不重叠、不丢表单数据。

## 10. 验收标准

### 10.1 全局验收

- 所有页面都有 loading、success，列表页还有 empty 和 error。
- 所有提交按钮都有 disabled 和 submitting。
- 所有失败都有 toast、错误态或可重试入口。
- 所有危险操作都有二次确认。
- 用户输入失败后不丢失已填内容。
- 路由未找到或 id 无效时有 not_found / error 展示。

### 10.2 核心路径验收

| 路径 | 必验状态 |
|------|----------|
| 登录 | 未勾协议、手机号错误、验证码倒计时、登录失败、登录成功 |
| 首页 | 热门案例加载成功、加载失败、创建项目跳转 |
| 我的页 | 用户信息加载、邀请码复制成功 / 失败、入口跳转 |
| 创作 | 未选素材、素材过多、时长非法、预估失败、权益不足、积分确认、重复点击 |
| 作品 | 空态、列表态、列表失败、详情成功、详情失败、播放失败、下载失败、过期 |
| 会员 / 积分 | 未勾协议、套餐加载失败、提交中、支付失败、支付成功占位 |
| 邀请 | 复制失败、分享失败、记录空态、记录加载失败 |
| 设置 | 清理缓存失败、退出登录确认、注销风险确认 |
| 反馈 | 描述为空、提交中、提交失败保留输入、提交成功 |

### 10.3 命令验收


若项目已有测试，再执行：

## 11. 编码注意事项

- 不要把 loading、empty、error 各写一套散落 UI，优先复用通用组件。
- Controller 中状态命名要统一，避免 `isLoading`、`loadingStatus`、`pageStatus` 混用。
- 表单提交失败必须保留用户输入。
- Mock 异常开关只能用于开发和验收，不要作为生产逻辑暴露。
- 不要因为真实接口待确定而省略错误态；后端越不确定，前端越需要 adapter 和状态兜底。
- 所有商业化、生成、注销等关键动作必须防重复提交。
- 状态验收是编码阶段收口任务，但建议每个模块实现时同步接入，最后再统一补漏。
- Flutter 模块完成或关键修复完成后，同步更新 `/Users/soul/code/lxwx/narrate/README.md` 的工程目录、业务功能、开发进度和待联调事项，README 作为用户查看当前 Flutter 开发进度的入口。
