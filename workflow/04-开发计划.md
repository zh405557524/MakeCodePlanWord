# 04 开发计划（plan.md）

目标：写一份**执行者照着做就不会走偏**的计划。前后端合在一份计划里，按功能切片排任务。计划经用户审核后才能开始写代码。

> 典型分工：Claude 写计划、审查结果；ChatGPT / Codex 执行。执行者不一定聪明，所以计划要写到"不需要猜"的程度。

---

## 1. 输入（写计划前必须读）

1. `scope.md`、`changes.md`（需求和验收标准）
2. 设计来源（`scope.md` 设计来源表、`doc/design/README.md`）
3. `doc/tech/` 基线（架构、接口、数据模型）
4. **每个涉及仓库的 `AGENTS.md` 和它索引的相关规范**（仓库规范目录，如 `.cursor/rules/`）
5. 相关的现有代码：要改的文件、可复用的组件和服务、相似功能的现有实现
6. `doc/testing/risk-checklist.md` 中本版勾选的领域

---

## 2. plan.md 的结构

模板见工作台 `templates/doc/versions/_template/plan.md`。各节要求：

### 0. 基本信息
版本、状态（草稿 / 已审核 / 执行中 / 完成）、涉及的仓库（绝对路径）、工作分支、执行者。

### 1. 本次已读规范（必填，缺这一节不予审核）

| 仓库 | 规范文件 | 和本计划相关的关键条款 |
|---|---|---|
| Solfeggio | AGENTS.md | 页面放 `lib/pages/{feature}/`，view/controller/index 三件套 |
| Solfeggio | .cursor/rules/01-conventions.mdc | 禁止在 View 中直接调 API |
| service | AGENTS.md | Controller 只做参数解析，业务进 Service |

关键条款要具体到"会影响本计划怎么写"的那几条。只写文件名不算读过。

### 2. 现状摘要
- 和本次相关的现有代码在哪：文件路径 + 一句话说明它现在做什么。
- 可以复用的组件、服务、工具方法：写出类名或函数名。
- 相似功能的参考实现：写出文件路径，要求执行者照着写。

### 3. 接口与数据契约（先定死，前后端共用）
- 新增或修改的接口：方法、路径、请求字段、响应字段。每个字段写类型、是否可空、单位、取值范围；**金额要写币种来源和精度，时间要写时区**。
- 错误码和对应的前端表现。
- 数据库变更：表、字段、索引、迁移脚本文件名、已有数据怎么处理。
- 配置变更：哪个配置文件、哪个 key、默认值。
- 架构级的变化（新服务、新存储、新三方）另写 `tech-design.md` 放在同一版本文件夹，这里只引用。

### 4. 任务列表
按**功能切片**排任务：一个任务 = 一个能单独验证的功能点，里面依次包含 后端 → 前端 → 测试。不要拆成"前端任务一组、后端任务一组"。

每个任务的固定格式：

```markdown
### T-03 订单保存商店实际币种
- 状态：待开始
- 关联需求：R-03（AC-03-1、AC-03-2、AC-03-3）
- 仓库与文件：
  - service（/Users/soul/code/soul/service）
    - 修改 src/main/java/.../order/OrderService.java：createFromReceipt()
    - 新增 src/main/resources/db/migration/V3.5__order_currency.sql
  - Solfeggio（/Users/soul/code/soul/Solfeggio）
    - 修改 lib/pages/membership/order_list/view.dart：金额显示
- 具体做法：
  1. 迁移脚本：order 表新增 currency VARCHAR(3) NOT NULL DEFAULT 'XXX'（XXX 表示历史未知）……
  2. OrderService.createFromReceipt()：从回执的 xxx 字段读取币种……；缺失时 ……
  3. 前端用现有 utils/money_format.dart 的 formatMoney(amount, currency) 显示，不要新写格式化函数
- 不要做：不要修改支付回调的验签逻辑；不要改动订单状态机
- 验证：
  - ./gradlew test --tests '*OrderServiceTest*'
  - flutter test test/pages/membership/order_list_test.dart
  - 对应用例：TC-12、TC-13、TC-14（见 test.md）
- 完成标准：上述测试通过；新增测试覆盖 AC-03-1～3
- 结果：（执行者完成后填写：做了什么、提交号、偏离计划之处）
```

### 5. 不改动范围
明确列出本次不能碰的目录、文件、接口、配置，防止执行者"顺手"扩散。

### 6. 风险与回滚
- 高风险点：数据迁移、支付、账号、并发。
- 回滚方式：迁移能否回退、开关怎么关、旧版本 App 是否兼容新接口。

### 7. 执行顺序
任务依赖关系、哪些可以一起做。

### 8. 调整记录
计划审核后的任何修改，追加一行：日期、改了什么、原因。

---

## 3. 任务粒度

- 一个任务的改动能在一次审查中看完（一般不超过 10 个文件）。
- 每个任务完成后，代码能编译、测试能通过，不留半成品。
- 一个任务只对应一个功能点；"顺便重构"单独成任务，并且要用户同意。

## 4. 测试用例和计划一起写

写计划的同时，在 `test.md` 写好本版新增用例（规则见 `06-测试验收.md`）：

- 每条验收标准（AC）至少对应一条用例。
- 每个任务的"验证"里写出它负责的用例 ID。
- 能自动化的（单元测试、接口测试）要求执行者在任务里实现；不能自动化的（真机、真实商店、实体设备）标为人工用例。

## 5. 写给执行者的硬要求

计划会直接交给执行 AI，所以：

- **不写模糊词**："按需""酌情""适当""优化一下""参考现有实现"都不允许单独出现，必须写出具体文件、具体做法。
- **写全路径**：文件写仓库内完整路径；跨仓库的写清是哪个仓库。
- **写出名字**：新增的类、方法、字段、路由、多语言 key 都给出名字。
- **写出复用对象**：已有的组件、工具方法、服务，写出名字并要求复用，不许重写。
- **写出验证命令**：每个任务都有能直接运行的命令。
- **给数据例子**：涉及数据格式的给出示例值（例如 `{"currency":"BRL","amount":"129.90"}`）。
- **写出停止条件**：在计划开头写明"遇到计划没写到的情况，停下来报告，不要自行扩展"。

## 6. 小改动的简化写法

改动小（一两个文件、半天以内）时，plan.md 可以只有：已读规范、文件清单和做法、不改动范围、验证命令和用例。但这几项一项都不能少。

## 7. 计划审核后的调整

需求在开发中变了（`changes.md` 有调整记录）时：

| 受影响的任务状态 | 怎么改 |
|---|---|
| 待开始 | 直接修改任务内容 |
| 进行中 | 修改任务内容，并在"结果"里注明"做到一半时计划调整：……" |
| 已完成 | **不改旧任务**，新增一个任务："T-09 调整：R-03 改为……（替代 T-03 的第 2 步）" |

每次调整都要在第 8 节「调整记录」追加一行。改动大到推翻已审核的方案时，把计划状态改回"草稿"，重新审核。

## 8. 审核清单（审计划时逐项过）

- [ ] 「已读规范」具体到条款，并且计划确实遵守了这些条款
- [ ] 每条 AC 都有任务覆盖、有用例覆盖
- [ ] 接口字段写了类型、可空、单位；金额有币种和精度，时间有时区
- [ ] 每个任务都有文件路径、具体做法、验证命令
- [ ] 没有模糊词
- [ ] 不改动范围写了
- [ ] 数据迁移有回滚方案，旧版本 App 兼容性考虑了
- [ ] 勾选的高风险领域，在任务或用例里有对应处理

审核通过后，把状态改为"已审核"，写上审核日期。
