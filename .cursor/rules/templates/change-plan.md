# {项目名称} 变更计划

> 规则来源：`.cursor/rules/00-核心工作流程.mdc` 第五步「变更管控与版本化记录」
> 用途：以「变更条目」为单位，登记本迭代内进行中与已完成的变更，控制影响范围，避免小改动触发大面积重写。
> 维护规则：
> - 命中变更管控关键词（新增/修改/删除）必须先在「进行中变更」追加条目，再做任何代码或文档改动。
> - 一条变更状态变为 `done` 时，从「进行中变更」移动到「本迭代历史变更」并同步追加到 `change-log.md`。
> - 跨迭代累积日志由 `change-log.md` 维护，本文件仅服务于「正在进行」与「本迭代」。

---

## 变更条目固定格式

每条变更（无论进行中还是已完成）都必须采用以下结构：

```markdown
### [CHG-{seq}] {一句话标题}

- 版本号: v{major}.{minor}.{patch}（编码期 patch++；新增模块 minor++；推翻重做 major++）
- 提出时间: YYYY-MM-DD HH:mm
- 类型: feature_add | feature_modify | feature_remove
- 触发原因: （用户原话 + 上下文）
- 影响范围:
  - 需求文档: 是/否 + 具体小节
  - Figma 设计计划: 是/否 + 具体页面
  - 技术方案: 是/否 + 具体章节
  - 工时评估: 是/否 + 增量工时估计
  - Flutter 模块: 是/否 + 具体模块/页面/文件
  - Kotlin 模块: 是/否 + 具体接口/Service/Repository
- 最小改动清单:
  - 必要新增: 文件 A、字段 B、接口 C
  - 对应修改: 文件 D 的 X 方法、组件 E 的 props
  - 必要删除: 文件 F、字段 G（含数据迁移说明）
- 不应改动范围: （明确写出本次不动的目录/文件/接口，防止扩散）
- 验收标准: 1) ... 2) ... 3) ...
- 回滚说明: （如何撤销该变更）
- 状态: pending | in_progress | done | rolled_back
- 关联恢复点: workflow.md 当前阶段编号 + 当前步骤
```

变更类型扩展枚举（仅在用户明确要求时使用）：

| 类型 | 含义 |
|------|------|
| `feature_add` | 新增功能 |
| `feature_modify` | 修改已有功能 |
| `feature_remove` | 删除已有功能 |
| `refactor` | 局部或模块级重构，必须由用户明确要求 |
| `rewrite` | 大范围重写，必须由用户明确要求 |

## 第一区块：进行中变更（pending / in_progress）

> 顶部区块。命中变更管控关键词时，新增条目放这里。
> 状态变为 `done` 时立刻移动到下方「本迭代历史变更」并同步到 `change-log.md`。

### [CHG-0001] {示例标题：占位，可删除}

- 版本号: v0.1.0
- 提出时间: YYYY-MM-DD HH:mm
- 类型: feature_add
- 触发原因: （示例：用户在编码阶段要求新增「夜间模式开关」）
- 影响范围:
  - 需求文档: 是 / `requirements.md` §X.Y
  - Figma 设计计划: 是 / 设置页 + 全局 Token
  - 技术方案: 否
  - 工时评估: 是 / +2 人天
  - Flutter 模块: 是 / `lib/pages/settings/`、`lib/theme.dart`、`lib/store/config.dart`
  - Kotlin 模块: 否
- 最小改动清单:
  - 必要新增: `lib/pages/settings/widgets/theme_switch.dart`、`ConfigStore` 中的 `themeMode` 字段
  - 对应修改: `lib/theme.dart` 增加 dark 主题、`MaterialApp` 接入 themeMode
  - 必要删除: 无
- 不应改动范围: 业务页面 controller、其他设置项
- 验收标准:
  1) 设置页有开关且持久化
  2) 切换后即时生效
  3) 重启后保留上次选择
- 回滚说明: 删除新增文件、恢复 `lib/theme.dart` 与 `ConfigStore` 的对应字段
- 状态: pending
- 关联恢复点: workflow.md 第 13 阶段（Flutter 编码 - 设置模块）
