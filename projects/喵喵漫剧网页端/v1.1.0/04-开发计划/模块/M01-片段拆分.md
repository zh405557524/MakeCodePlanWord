## 3. 现状摘要

后端（`src/main/java/com/lxwx/narrateservice/app/catdrama/`）：

1. 单集拆分是两步：模型拆**镜头**，程序把镜头**组合**成片段。组合在 `analysis/domain/DramaSegmentComposer`：
   - `composeSegments(CameraShotParse parsed, String sourceText, int durationLimitSeconds, boolean multiShotAllowed, Options)` → `Composition(segments, issues, cameraShots)`：按时长上限贪心装箱，只在镜头之间断开，同场景内均衡过短尾段；`segments` 是 `LenientShot`（序号从 1 连续），`cameraShots` 是每个镜头放进了第几个片段。
   - `composeSingleSegment(...)`：“生成提示词”专用，**全部镜头拼成一个片段，不按时长拆**（注释写着“片段数量不能变”）；超长由调用方记 `MODEL_DURATION`。
   - 两者拼出的提示词写法完全一样（都用 `segmentDescription`）。
2. 镜头存在 `catdrama_camera_shots`（`DramaCameraShotService`，analysis 包）：一行一个镜头，`analysis_id` = 哪一次拆分，`segment_ordinal` = 放进了第几个片段，`source_anchor` 是相对**本集剧本**的位置，`asset_markers` / `sound_markers` 是那次任务里的短标记（`asset_001` 这种，按本集素材 ID 排序编号，跨任务不稳定）。当前生效的一批 = 剧集 `applied_analysis_id` 那一批；`GET /episodes/{id}/camera-shots` 按 `analysis_id + ordinal` 把镜头对到片段上。
3. “生成提示词”（`DramaShotDescriptionService`）：
   - `submit`：快照里 `episode.text` = **这个片段的原文**（不是整集），`productionSettings` = **作品的**设置（`project.productionSettings()`，第 166 行），还有 `shotRevision`、`shotOrdinal`、`shotAnalysisId`、`shotSourceStart`（片段原文在本集剧本里的起点）、`registry`（本次的短标记注册表）。
   - `parseCameraShots`：读镜头 → `composeSingleSegment` → 超长记 `MODEL_DURATION`。镜头的原文位置是相对**片段原文**的。
   - `COMMIT_DELIVERY`（约第 277 行）：先 `writer.replaceGenerated(...)`（片段版本没变才替换描述，自己的事务；重放时描述已一样按成功），再 `jobs.commit(SUCCEEDED/SUPERSEDED, 回调)`，回调里 `cameraShots.replaceSegmentCameraShots(..., input.shotOrdinal, ...)` 换这个片段的镜头。

- 具体做法：
  1. **用片段生效的设置**（`submit`）：`productionSettings` = 片段 `production_override`（转成 `DramaProductionSettings`）不为空就用它，否则 `project.productionSettings()`；两者都没有仍报“请先保存制作设置”。给模型的【片段生成设置】、`shotSplitSettings(input)` 算出的时长上限和“能否段内分镜”都跟着变。快照多存一个 `shotProductionOverride`（原样的 JSON，可为空），第 7 步给新片段用。
  2. **判断要不要拆**（`parseCameraShots`，`composeSingleSegment` 成功之后）：同时满足才试拆——
     - 上限 > 0，且拼成一个片段的总秒数 > 上限；
     - 快照里有 `shotAnalysisId` 和 `shotSourceStart`（新版拆分的片段）。
     试拆：`composeSegments(parsed, source, 上限, 能否段内分镜, analysis.composerOptions())`（`source` 就是片段原文）。结果有 **2 个及以上片段**，并且**每个镜头都放进了片段**（`composition.cameraShots().size()` 等于镜头数，没有因提示词超字数被跳过的）→ 拆；否则照现在写回一个片段 + `MODEL_DURATION`（单个镜头自己就超长时 `composeSegments` 只会得到它单独一组，也走这里——AC-02-3 靠这条：拆完仍有某一部分超长，也算“拆不开”，整体不拆）。
     > 注意：`composeSegments` 遇到新场景、不能段内分镜等也会断开。所以**只有超长时才调用它**，不超长时一律不拆、和现在完全一样。
  3. **拆分结果**放进 `Generated.parts`，每部分：提示词（`LenientShot.description`）、原文（`LenientShot.sourceText`，片段原文的一段）、相对片段原文的起止位置、素材标记 / 声音标记、时长、这一部分的镜头（`List<CameraShot>`）、检测问题（这一部分镜头的问题；`parsed.issues()` 整段问题放第 1 部分）。检测问题的片段号**先记成第几部分**，写回时再换成片段当前序号（第 6 步）。`Generated.description` / `problems` / `cameraShots` 仍填“拼成一个片段”的结果（拆不成时用它）。
  4. **把每部分换成候选**（`ShotCandidate`）：`candidateKey` 随机 UUID；`sourceText` = 这一部分的原文；`sourceAnchor` = `{start, end, fingerprint}`，`start/end` = 相对片段原文的位置 + `shotSourceStart`（换成相对本集剧本），`fingerprint` = `DramaMarkdownContentReader.sha256(这一部分原文)`（和 `DramaSegmentComposer#segmentOf` 一致）；`markers` / `soundMarkers` = 这一部分的标记；`problems` 见第 3 步。出场素材对应：`selected = assets.previewAnalysisBindings(userId, episodeId, 快照 registry, 全部标记)`（照 `AnalysisDiffService#buildDiff` 的写法注入同一个素材服务）。
  5. **分镜头的素材标记存成稳定写法**：写回分镜头表之前（拆或不拆都做），把每个镜头 `references()` / `soundReferences()` 里的短标记，按本任务快照的 `registry` 换成 `[素材:素材ID]`；注册表里查不到的原样保留。原因：短标记按“本集当前素材”临时编号，B-02 以后要把不同任务写的镜头放在一起组合，短标记会对错素材。整集分析 `saveCameraShots` 存的短标记**不动**（它们能用那次分析记录里的注册表换回来，B-02 第 4 步）。
  6. **写回（拆分时）**——不拆时保持现在的写法，只把回调里的 `input.path("shotOrdinal")` 换成片段当前序号（防止前面的片段刚被拆过、序号已顺延）：
     a. 先读片段：不是有效片段，或版本 ≠ `shotRevision` → 和现在一样记 `SUPERSEDED`，不写、不拆。

     c. `jobs.commit(SUCCEEDED, "DESCRIPTION_READY", …, 回调)`，回调里（和任务置成功同一个事务）：`projects.withAnalysisTarget(userId, episodeId, …)` 加作品锁 → `shots.splitShot(...)` → `cameraShots.replaceSegmentCameraShots(..., k, parts 的镜头, shotSourceStart, now)`（第 8 步的新重载）→ `projects.assetBindingChanged(userId, episodeId, 剧集当前版本, now)`（本集版本号 +1）。
     d. `splitShot` 发现版本或序号变了会抛 `CATDRAMA_REVISION_CONFLICT`，整个提交回滚。分两种情况：
        - **只是序号变了、片段版本没变**（网页可以同时对几个片段点“生成提示词”：前面的片段先拆完，后面片段的序号就顺延了，而 b 步算 `k` 时还没拿到作品锁）：这不是冲突。回滚后**在 `COMMIT_DELIVERY` 这一步里重新从 a 做一遍**（重新读片段、重新算 `k` 和 `segmentSplit`、再提交），最多重做 2 次；还是不行再按下一条处理。新片段 ID 可以复用第一次生成的。
        - **片段版本变了**（或重做 2 次仍冲突）：执行者核对工作流对“提交回调抛异常”的处理——回滚后再次执行 `COMMIT_DELIVERY` 会走到 a 记 `SUPERSEDED`，或任务记失败，两种都可以接受（原片段不变），在“结果”里写明是哪种。

## 9. 风险与回滚

1. “本集设置”取的是序号最小的有效片段的生效设置（D-20）。网页只能整集统一设置，正常各片段一样；本集是第一次生成（还没有片段）时用作品设置。
2. 本集各片段设置不一样时（只可能来自手机端单独改某个片段），“片段拆分”按序号最小的片段的设置组合，可能和别的片段的设置不一致；网页只能统一设置，正常不会出现。
3. 老数据：本版之前“生成提示词”写进分镜头表的是短标记。B-02 用生效分析记录的注册表换素材 ID——那次“生成提示词”之后本集**删过**素材时可能对错素材（新加素材不影响，编号按素材 ID 排序往后加）。影响范围：只是“新增”片段的出场素材；差异弹框里能看到，用户可在应用后手动改。
4. “片段拆分”有变化的片段换成新组合：手改过的提示词不会带过去（弹框说明里已写明，原片段进历史可找回）。
5. 拆分任务跑的几秒里，本集 `shotGeneration` 是“生成中”：网页本页不切等待面板（F-03 第 5 步）；手机端此时打开这一集会短暂显示加载页（M-01 核对）。
6. “生成提示词”拆分后本集版本号 +1：别处拿着旧版本号的操作会收到 `-560001`，网页已有刷新处理；手机端见 M-01 第 5 项。
7. 回滚：后端撤回 §6.1 的文件改动即可（没有表结构和数据迁移；已拆出的片段是普通片段，留着不影响旧代码；分镜头表里 `[素材:ID]` 写法旧代码不读）。网页端撤回 §7 列出的文件。
