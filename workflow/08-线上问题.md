# 08 线上问题（patch 版本 / fix.md）

目标：线上 bug 用最轻的流程修好，并且保证同类问题下次能在测试阶段被发现。

## 1. 先分类

| 问题类型 | 处理 |
|---|---|
| 线上 bug：行为和基线描述不一致 | 开 patch 版本（本文） |
| 基线本身写错了、规则需要改 | 小的开 patch，并在 `fix.md` 写明基线要改哪里；大的进下个功能版本 |
| 体验问题、新需求 | 写进 `backlog.md` |
| 崩溃、资金错误、数据损坏 | 开 patch，优先处理；必要时先暂停放量或关闭相关开关 |

## 2. patch 流程

1. 创建：`scripts/new-version.sh <docRoot> <版本号> --patch`（例如上一个发布是 v2.0.1，就开 v2.0.2）。
2. 写 `fix.md`（模板见 `templates/doc/versions/_template-patch/fix.md`）。一个 patch 可以修多个问题，每个问题一节（F-01、F-02……）：
   - 现象：用户看到什么、影响多少用户、从哪个版本开始
   - 复现：步骤、环境（地区、币种、设备、账号类型）
   - 原因：定位到代码或配置的具体位置
   - 修复方案：改哪些文件、怎么改（格式同 `plan.md` 任务，必须有"已读规范"）
   - 数据修复：已经产生的错误数据要不要修、怎么修（脚本、范围、备份）
   - 验证：自动化测试 + 数据链路检查 + 回归范围
   - **防再发**：补进 `regression.md` 的用例、补进 `risk-checklist.md` 的维度
3. 用户确认修复方案（紧急时可以和发布确认合并为一次）。
4. 按 `05-开发执行.md` 修复、验证。
5. 按 `07-发布.md` 发布。patch 的收尾只需要：
   - 用例合并进 `regression.md`，维度合并进 `risk-checklist.md`
   - 如果修复改变了产品行为或接口，同步 `doc/product/`、`doc/tech/`
   - 更新 `doc/README.md`，打 tag

## 3. "防再发"必须做

每个线上 bug 修完都要回答：**为什么测试阶段没发现？**

- 缺用例 → 在 `regression.md` 补一条能复现它的用例。
- 缺维度（例如只用一个地区账号测过）→ 在 `risk-checklist.md` 加一条检查维度，写明来源。
- 用例只查了界面没查数据 → 在用例里补"预期（数据）"，并检查同模块其他用例有没有同样的问题。

这一步写在 `fix.md` 的"防再发"里，发布收尾时合并进 `doc/testing/`。

## 4. 主分支上已经有未发布的新功能时

1. 从上一个发布 tag 拉分支：`git switch -c hotfix/vX.Y.Z vX.Y.(Z-1)`。
2. 在 hotfix 分支上修复、测试、出包、发布，并在这个分支上打 tag。
3. 把 hotfix 分支合回主分支。如果开发中版本也改了同一块代码，在开发中版本的 `plan.md` 加一个任务处理冲突。
4. 开发中版本的 `changes.md` 如果和这次修复有关，在对应条目的调整记录里注明。

后端是多 App 共用的，修复前先确认改动不影响其他 App；影响的话在 `fix.md` 写清楚，并跑其他 App 的相关测试。

## 5. 只改后端、不发 App 的修复

App 版本号不变，但修复已经上线：

- 记在下一个 patch 版本的 `fix.md` 里（还没有就新开一个），这一节写明"仅后端，已于 YYYY-MM-DD 上线"，以及后端版本号和提交号。
- "防再发"照常做，用例和风险维度可以马上合并进 `doc/testing/`，不用等 App 发版。
- 接口行为变了的，马上同步 `doc/tech/api.md`；产品行为变了的，同步 `doc/product/`（基线描述的是线上现状，后端上线就算线上）。
- 后端仓库打 tag：`{appCode}-backend-{后端版本号}`，例如 `solfeggio-backend-5.0.0`。
