# 00 总流程

> 适用：一个人 + AI 做 App。可以是 Claude 出文档和计划、ChatGPT / Codex 执行，也可以一个 AI 全程。
> 本文是总纲；`01`～`11` 是细则，进入哪个阶段再读哪一份。每个阶段用哪个提示词，看工作台根目录 `工作说明.md`。
> 旧版 01–19 阶段规则在 `legacy/v1/`，只供追溯。

---

## 1. 八个阶段

```
产品 → 设计 → 技术规划 → 开发计划 → 开发 → 测试 → 上线 → 归档
```

| 阶段 | 细则 | 产出（都在版本文件夹里） | 用户确认 |
|---|---|---|---|
| 1 产品 | `01-产品.md` | `01-产品/` 四份：需求清单、本版产品需求、用户评审版、独立检测报告 | ✅ 需求清单；✅ 检测通过且用户明确确认 |
| 2 设计 | `02-设计.md` | `02-设计/`：设计说明、设计计划；参考图片、Figma 稿及切图 | ✅ 先检查图片，通过后才画 Figma；✅ 再确认 Figma（不出稿须明确确认） |
| 3 技术规划 | `03-技术规划.md` | `03-技术规划/`：**完整技术文档**（架构、接口、数据模型）、本版技术方案 | ✅ |
| 4 开发计划 | `04-开发计划.md` | `04-开发计划/开发计划.md`，同时在 `05-测试/测试.md` 写好用例 | ✅ 审核后才能写代码 |
| 5 开发 | `05-开发.md` | 代码；进度写在开发计划的任务状态里 | 遇到计划外情况才问 |
| 6 测试 | `06-测试.md` | `05-测试/测试.md`：执行结果、缺陷、结论 | 看结论，决定遗留问题 |
| 7 上线 | `07-上线.md` | `06-上线/上线记录.md`：出包、审核、放量、上线观察 | ✅ |
| 8 归档 | `08-归档.md` | 本版已上线增量合入 `当前产品文档/`；用例并入项目 `testing/`；更新 `README.md`；冻结版本文件夹、打 tag | ✅ |

另外三份：

- 线上出 bug：`09-线上问题.md`。开 patch 版本，只写一页修复单，不走全套。
- 新项目：`10-新项目初始化.md`。
- v1 旧工作区的项目：`11-旧项目迁移.md`。

改动很小的版本，每个阶段的文件可以写得很短，但**不能跳过开发计划审核**。

## 2. 文件放在哪

**工作区和代码分开。** 每个项目在工作台 `projects/{项目名}/` 有一个工作区，放全部文档；代码仓库只放代码、编码规范和一份指向工作区的 `AGENTS.md`。

```
projects/{项目名}/
├── README.md        线上版本、开发中版本、版本列表（一页）
├── 当前产品文档/     线上已完成的功能：00-总纲.md + 模块分册。归档时合入已上线增量
├── backlog.md       想法池（跨版本）
├── testing/         跨版本累积：regression.md 回归用例、risk-checklist.md 高风险清单
├── history/         迁移前的旧文档（只读，不作为依据）
├── v2.1.0/          已归档（只读）
├── v2.1.1/          patch：修复单.md
└── v2.2.0/          开发中
    ├── README.md      版本说明：状态（到哪一步）、每个文档在哪
    ├── 01-产品/       requirements-list.md、requirements.md、requirements-review.md、detection-feedback.md
    ├── 02-设计/       设计说明.md、设计计划.md
    ├── 03-技术规划/   architecture.md、api.md、data-model.md、技术方案.md
    ├── 04-开发计划/   开发计划.md
    ├── 05-测试/       测试.md（证据放 evidence/）
    └── 06-上线/       上线记录.md
```

- **当前产品文档** = 线上全量定义，只有一份。版本 `requirements.md` = 本版集中增量；需求分析用全量基线 + 本版已确认增量，未改功能直接引用基线。
- 版本内设计说明、架构 / 接口 / 数据模型描述做完后的样子；产品需求只写变化，用户评审版核对变化及受影响的完整链路。需求清单包含原改动清单的 R / AC / 来源，检测独立留痕，不增加第五份产品文档。
- 项目工作区登记在工作台 `workspace-registry.json` 的 `workspace` 字段。
- 代码仓库根目录 `AGENTS.md` 写明工作区的绝对路径，AI 在仓库里写代码时按路径去读开发中版本的文档。
- 后端多 App 共用时，后端仓库的 `AGENTS.md` 按 App 列出各自的工作区。
- 大文件（设计出图、切图、测试录屏）放工作区的 `design-assets/` 等目录，不放进版本文件夹。

## 3. 版本怎么延续

1. **线上是什么样 = `当前产品文档/`。** 修线上 bug、开新版本都以它为准。patch 改了产品行为时，patch 归档时直接改它（见 `09`）。
2. **新版本预期 = 全量基线 + 本版已确认增量。** 版本 `01-产品/requirements.md` 集中写变化；未批准规则明确待定。
3. **开新版本 = 四份产品模板 + 沿用设计、技术文档。** `scripts/new-version.sh` 不复制全量产品；`--from` 指定参考版本及设计、技术来源，来源内容不修改。
4. **归档 = 合并 + 冻结 + git tag。** 按 `08` 将已上线的 R 逐项合入 `当前产品文档/`，保留所有未改功能；不能用增量覆盖全量。冻结版本，工作台打 `{appCode}-vX.Y.Z`，代码仓库另打 `vX.Y.Z`。
5. **状态写在文档里，过程写在 git 提交里。** 不维护流水账式的 `workflow.md`、`change-plan.md`、`change-log.md`。

想看什么，去哪里找：

| 想知道 | 看哪里 |
|---|---|
| 线上产品现在是什么样 | `当前产品文档/` |
| 新版本做完后是什么样 | `当前产品文档/` + 开发中版本 `01-产品/requirements.md`；设计和技术看本版 `02-设计/`、`03-技术规划/` |
| 阅读并评审本版产品需求 | `01-产品/requirements-review.md`：受影响的完整链路、涉及页面、规则、异常和待确认事项 |
| 文档有没有问题、能否进入设计 | `01-产品/detection-feedback.md`：独立检测结论、问题与复检、用户确认状态 |
| 这一版改了哪些地方 | `01-产品/requirements.md` 正文，`requirements-list.md` 的 R / AC / 来源；技术改动看技术方案 |
| 做到哪一步了 | 版本 `README.md` 顶部的状态；`04-开发计划/开发计划.md` 的任务状态；`05-测试/测试.md` 的结论 |

## 4. 版本号与状态

**版本号 = 商店版本号**（`major.minor.patch`），构建号另计。

| 升哪一位 | 什么时候 |
|---|---|
| minor | 有新功能、改版、付费或权益变化、数据结构变化。走全部八个阶段 |
| patch | 只修 bug、改文案、小调整。只写修复单（见 `09`） |
| major | 产品大改、推倒重来 |

版本状态写在版本 `README.md` 顶部（patch 写在修复单），并同步到项目 `README.md`：

`产品（需求分析 / 产品文档 / 评审）→ 设计 → 技术规划 → 开发计划 → 开发 → 测试 → 上线 → 已归档`

每个阶段的产出经用户确认后，状态改成下一个阶段。

产品阶段先生成本版产品需求与产品评审版，再独立检测、交用户评审，修改后复检。**检测通过且用户明确确认**才进入下一阶段；只同意结构、命名或格式不算批准业务规则。

自己出稿的设计子状态：**图片制作 → 图片待用户检查 → 图片通过 → Figma 绘制 → Figma 待用户确认**。图片未获用户明确通过，不进入对应范围的 Figma 绘制；Figma 确认后才进入技术规划。AI 自检与用户确认分别记录。

## 5. 改动怎么处理

| 情况 | 例子 | 处理 |
|---|---|---|
| 版本没上线，发现需求有问题 | 弹框文案、某条规则要改 | 直接改 requirements.md 对应位置，同步产品评审版，在 requirements-list.md 对应 R 追加调整记录，检测报告追加复检；受影响的设计、技术方案、开发计划跟着改（开发计划按 `04` 第 7 节） |
| 版本没上线，想加小功能 | 加收藏 | 写进 requirements.md，requirements-list.md 加 R / AC 并登记范围变更 |
| 版本没上线，想加大功能 | 新练习模式 | 写进 `backlog.md`，留给下个版本 |
| 版本没上线，不做某功能了 | 去掉一个页面 | 在本版需求撤销对应增量，requirements-list.md 标取消；不改全量基线；已写代码的在开发计划加"移除"任务 |
| 已上线，线上 bug | 订单币种不对 | 开 patch，按 `09-线上问题.md` |
| 已上线，做新功能 | 下一个版本 | `new-version.sh` 开新版本，从 `backlog.md` 挑范围 |
| patch 和新版本同时进行 | | patch 改了产品行为或接口的，归档时改 `当前产品文档/`，复核开发中版本是否与新基线冲突并更新引用及受影响增量（见 `09` 第 4 节） |

**大小怎么判断**：AI 一天内能做完、不改数据结构、不影响付费和权益 → 小；否则 → 大。拿不准就问用户。

## 6. AI 每次开始工作前必做

1. **确认项目**：在工作台查 `workspace-registry.json`；在代码仓库里读根目录 `AGENTS.md`。
2. **读项目 `README.md`**：知道线上版本和开发中版本。开发中版本可能同时有两个（一个 patch、一个功能版本），用户没说是哪个时先问，不要把一个版本的改动写进另一个版本。
3. **看开发中版本在哪个阶段**：看版本 `README.md` 顶部的状态。
4. **只读当前阶段的细则和需要的文件**，不通读整个工作区，也不一次读完 `workflow/`。
5. **要写代码时**，先读代码仓库的 `AGENTS.md` 和它索引的编码规范（见 `05`）。

---

## 7. 不要做的事

- 不修改已归档的版本文件夹（唯一例外见 `07` 第 3 节：另一个平台后上线时补上线记录）。
- 不为小改动新建流程文档；在当前版本的 requirements-list.md、开发计划里加一条。
- 不把执行过程（命令输出、尝试过程）写进文档；测试证据放 `05-测试/evidence/`，过程放 git 提交信息。
- 不跳过开发计划审核直接改代码。线上紧急修复也要先有修复单。
- 不把 `history/` 里的旧文档当开发依据。
