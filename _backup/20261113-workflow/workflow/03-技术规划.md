# 03 技术规划

目标：前后端一起想清楚这一版**技术上怎么做**，把接口和数据先定死；同时让完整技术文档反映这一版做完后的样子。

## 产出（`vX.Y.Z/03-技术规划/`）

| 文件 | 是什么 |
|---|---|
| `architecture.md` | **完整**：技术栈、仓库、分层、关键流程、环境与配置、三方服务 |
| `api.md` | **完整**：前后端共用的接口契约。字段明细只写在这里 |
| `data-model.md` | **完整**：服务端表结构、App 本地存储、枚举与状态 |
| `技术方案.md` | **本版**：每条产品改动在前端、后端、数据、配置上怎么做；接口和数据改了哪些；兼容和上线顺序；风险 |

技术文档仍按全量维护（与本版产品增量不同）：三份完整文档开版本时从上一版复制过来，直接改成新版本的样子，改过的小节下面加 `> 本版改动：R-xx`。

## 输入

1. `当前产品文档/` 相关模块 + 本版 `01-产品/requirements.md` 集中增量；`01-产品/requirements-list.md` 的 R / AC；未决冲突不得直接实现
2. 本版 `02-设计/`：设计计划、Figma（页面结构、组件、状态）
3. 本版 `03-技术规划/` 里复制来的完整技术文档
4. 每个涉及仓库的 `AGENTS.md` 和它索引的规范（如 `.cursor/rules/`）
5. 相关的现有代码：要改的模块、可复用的组件和服务、相似功能的现有实现
6. 项目 `testing/risk-checklist.md` 中本版勾选的领域

## 1. 写技术方案

模板见工作台 `templates/version/03-技术规划/技术方案.md`：

1. **改动对照**：每条 R 一行，写它在 App、后端、数据库、配置、三方上分别要动什么；不涉及的写"无"。
2. **架构变化**：新服务、新存储、新三方、新的跨端流程。没有写"无"。有的话同步改 `architecture.md`。
3. **接口变化**：列出新增 / 修改 / 废弃的接口，每个一行，链接到 `api.md` 的小节；写为什么这样设计、前端怎么调用、错误码对应的前端表现。
4. **数据变化**：表、字段、索引、迁移脚本文件名、存量数据怎么处理、能不能回退；App 本地存储的变化和老数据升级。字段写进 `data-model.md`。
5. **配置与开关**：哪个配置、哪个 key、默认值；需要灰度或开关控制的功能怎么关。
6. **前端方案**：页面和路由、状态管理、要复用的组件和服务（写出名字和路径）、多语言 key 的范围。
7. **后端方案**：服务和模块划分、事务和并发、权益校验、多 App 共用时对其他 App 的影响。
8. **兼容与上线顺序**：旧版本 App 访问新接口会怎样；先上后端还是先上 App；迁移什么时候跑。
9. **风险**：本版勾选的高风险领域，在技术上怎么保证（例如金额全链路带币种、迟到的响应不写进已切换的账号）。
10. **待确认**：需要用户拍板的技术选择。

## 2. 改完整技术文档

- **`api.md`**：新增和修改的接口写完整：方法、路径、鉴权、请求字段、响应字段、错误码、示例。每个字段写类型、是否可空、单位、取值范围；**金额写币种来源和精度，时间写时区**。废弃的接口标"废弃（vX.Y.Z）"，下线后再删。
- **`data-model.md`**：改表、加字段、加枚举值都写进来；迁移脚本的最新版本号更新。
- **`architecture.md`**：只有架构变化时才改。

接口字段只在 `api.md` 写一次；技术方案和开发计划都引用它，不重复字段表。

## 3. 写法要求

- 前后端在同一份方案里，按功能（R 编号）组织，不拆成"前端方案一份、后端方案一份"。
- 写具体：路径、类名、表名、字段名、配置 key 都写出来。"按需""酌情""参考现有实现"不单独出现。
- 现有代码里有可复用的，写出名字和路径，开发计划会要求执行者复用。
- 改动小的版本，技术方案可以只有几行；但只要接口或数据有变化，`api.md`、`data-model.md` 就要改。

## 4. 自检清单

- [ ] 每条 R 在改动对照里都有一行
- [ ] 接口字段写了类型、可空、单位；金额有币种和精度，时间有时区
- [ ] `api.md`、`data-model.md` 已经是本版做完后的样子，改过的小节有本版改动标记
- [ ] 数据迁移写了存量数据处理和回退方式
- [ ] 旧版本 App 的兼容、上线顺序写了
- [ ] 勾选的高风险领域，在第 9 节都有对应
- [ ] 多 App 共用后端时，写了对其他 App 的影响

## 5. 交给用户确认

列出技术方案的要点和待确认项。确认后版本 `README.md` 状态改为"开发计划"。

开发计划阶段发现契约要改：先回来改技术方案和 `api.md` / `data-model.md`，再改计划。
