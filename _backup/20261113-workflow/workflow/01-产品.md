# 01 产品

目标：版本产品目录只保留四份文档。**全量产品定义在项目的 `当前产品文档/`，版本文档写本次增量**，不再复制一套全量分册。

```
需求清单 →【用户确认范围】→ 本版产品需求 + 产品评审版 → 独立检测 → 用户评审 → 修改并复检 →【检测通过且用户明确确认】→ 设计
```

## 产出（`vX.Y.Z/01-产品/`）

| 文件 | 职责 | 主要读者 |
|---|---|---|
| `requirements-list.md` | 用户原话、材料、需求分析、做 / 不做、R 编号、AC、来源、范围变更与调整记录 | 用户确认范围；技术、开发、测试追溯 |
| `requirements.md` | **本版产品需求正文**：集中写本次新增、修改、删除后的行为、流程、页面、规则、状态和异常；未改内容链接全量基线 | 设计、技术规划、开发和验收 |
| `requirements-review.md` | **给用户看的产品评审版**：用易读方式核对本版需求及受影响的完整用户链路，保留逐项决策 | 用户阅读、核对和拍板 |
| `detection-feedback.md` | **独立检测报告**：检测范围、问题、证据、历轮结论、复检及用户确认状态 | 判断文档质量和下一阶段资格 |

不再单独生成需求分析、改动清单或本版全量产品分册。设计素材可以放引用目录，不能变成另一套有效需求。

## 1. 需求清单

输入：用户想法和材料、`backlog.md`、反馈、线上数据、`当前产品文档/`、`testing/risk-checklist.md`。

先用 `scripts/new-version.sh <工作区> vX.Y.0` 开版，再更新项目 README 的开发中版本。脚本只为产品生成四份空模板，设计和技术文档仍可沿用上一版；`--from` 指定参考版本，不把它的产品正文当作线上基线。

在 `requirements-list.md` 写：
- 用户原话、材料位置及日期；需求背后的问题和依据。
- 做 / 不做、涉及模块、高风险领域、3～8 条可观察的版本验收标准。
- 每条需求一个稳定的 `R-xx`，标类型、位置、摘要、原因和来源（用户提出 / 材料记载 / 推导）。编号不复用。
- 每条 R 有 `AC-条目号-序号`。钱、账号、权益、同步必须写数据结果；多语言、多地区、多设备写覆盖组合；失败和边界不能遗漏。
- 假设、待确认、范围变更和调整记录。业务长篇正文只写在 `requirements.md`，这里链接对应小节。

先交用户确认需求范围；确认要有日期和直接依据。“下一步”或同意文件结构不等于批准所有假设。

## 2. 本版产品需求

在一份 `requirements.md` 内按业务模块组织，不把开发需要的同一条链路拆散到多个补充文件。

- 开头明确版本、状态、基线入口与版本 / 日期、参考 patch 或来源版本。未归档来源不是线上事实。
- 列本版改动及 R 编号，明确不变和不做的范围；新版本预期 = **当前全量基线 + 本版已确认增量**。
- 改动用“基线行为 → 本版目标”说清差异，然后完整写目标流程。未改业务不复制；链接到基线具体模块和章节。
- 新增或有交互变化的页面按顺序写：页面定位、参考素材、页面结构、区块说明、主要功能、交互流程图（Mermaid）、详细交互、关键状态与异常、AC 引用。只改视觉的页面仍登记用途、核心操作和去向，但业务详情沿用基线。
- 价格、积分、次数、时长、额度、有效期写来源、刷新及失败行为，不把示例图数字写成固定业务值。
- 删除明确影响的入口、状态和数据处置；取消的 R 保留记录。不得为取消本版增量而改动当前基线。
- 推导标“推导，待确认”；原材料有冲突就地列双方口径、证据与检测编号，不自行裁决、不覆盖已有明确确认。
- 详细验收标准仅在 `requirements-list.md` 维护，正文按 R / AC 引用。

全量基线只在上线归档时按已交付增量合并更新（见 `08`）。新项目没有基线时，首版所有功能都是新增，仍在一份 `requirements.md` 中写完整首版定义。

## 3. 产品评审版

`requirements-review.md` 与开发需求是两份文档，不能互相冒充或合并。固定 11 节，没有内容写“本版无”：
1. 一句话版本。
2. 本期范围（做 / 不做）。
3. 产品全景流程：包含变化所在的完整用户链路，8～15 个用户节点。
4. 页面地图：本版涉及页面的 ID、用途、核心操作、去向和变化；弹框另计。
5. 逐页面功能 Checklist：与地图对应，列关键操作条件、结果、失败恢复；弹框列触发和按钮结果。
6. 核心业务规则。
7. 必须人工确认的产品决策。
8. 异常与边界行为。
9. 用真实场景反向 Review（5～15 个，优先失败、重复操作、历史数据、跨页面联动）。
10. 状态变化速查。
11. 已确认 / 待确认（日期与依据）。

以 5～10 分钟读懂主干为目标。普通增量版本不用重写全部旧页面；**全量视觉改版涉及全部页面，必须逐一登记**，不能用“其余页面只换视觉”代替。详细变化链接 `requirements.md`，未变规则链接当前基线；不重复长篇正文，不写实现细节。冲突关联检测编号；已确认决策不能在另一个表里悄悄变回待定。

## 4. 独立检测与用户评审

AI 对照全量基线和四份版本文档检测，写入 `detection-feedback.md`，再把评审版与报告一同交用户。

| 维度 | 检查 |
|---|---|
| 结构 | 四份职责明确；需求集中；受影响链路、页面字段、流程图齐全；没有复制全量基线 |
| 范围 | 与已确认的做 / 不做一致，原材料每项有去处 |
| 一致 | R、正文、AC、评审版和决策状态对应；基线引用明确；冲突未被隐藏 |
| 验收 | 每条 R 有 AC；资金等写到数据；失败、空、离线、无权限、重复操作有覆盖 |
| 决策 | 推导和未确认可辨认，确认有直接依据；高风险未决项列阻塞 |
| 评审版 | 11 节完整；本版涉及页面、弹框不遗漏；用户能读懂流程和操作结果 |

报告记录实际检查范围、日期、依据、结论（未执行 / 通过 / 不通过）。每个问题有稳定编号、优先级、位置、证据、影响、建议、处理状态。建议不是批准，整理不是修复。

保留历轮原始结论和问题，追加复检与用户意见，不覆盖失败证据；材料变动后注明旧结论哪些待复检。

**检测通过且用户明确批准产品**后才改版本和项目 README 为“设计”；本版不出稿也须明确确认并记录，才能进技术规划。否则保持“产品·评审”。确认命名、格式或结构不等于批准业务。资金、账号、权益、数据安全及核心流程的高风险未决项不能带入开发计划。

## 开发中调整

修改 `requirements.md`，同步评审版；在 `requirements-list.md` 对应 R 追加调整记录，范围变化单列；检测报告追加复检。受影响的设计、技术和开发计划同步（开发计划见 `04` 第 10 节）。大功能放 backlog，不中途塞入。

材料记载不等于用户确认；文档写好不等于业务批准；产品文档不写技术实现细节。
