# 07 发布（release.md）

目标：把测试通过的版本安全地发出去，并在发布后把这一版的改动合并回基线。

构建、上架、灰度、监控不再是独立阶段，统一写在 `release.md` 的检查清单里。第一次上架某个商店时，另看 `参考/首次上架清单.md`。

---

## 1. 发布前检查

- [ ] `test.md` 结论为"可以发布"（含用户对阻塞项的决定）
- [ ] `plan.md` 任务全部完成，或未完成的已移到 `backlog.md`
- [ ] 版本号、构建号已确定（版本号 = `scope.md` 的版本；构建号只增不减）
- [ ] 后端：部署顺序（先后端还是先 App）、数据库迁移、配置变更已写清；旧版本 App 能兼容新接口
- [ ] 新增了数据收集、权限或三方 SDK 时：隐私政策、商店隐私表单、iOS 隐私清单已更新
- [ ] 付费相关改动：商店商品配置、价格、订阅说明已核对
- [ ] 商店素材（截图、描述）需要更新的已准备
- [ ] 用户可见的更新说明已写好（各语言）

## 2. 发布步骤

1. **构建**：按仓库 `AGENTS.md` 或规范目录里的构建说明出包（Android AAB、iOS IPA、后端部署包）。
2. **内部测试**：TestFlight / Google Play 内部测试轨道，安装正式包跑一遍冒烟用例。
3. **后端上线**：按部署顺序执行，迁移前先备份。
4. **提交审核**：被拒时把拒绝原因（Guideline 编号和原文）和处理记录在 `release.md`。只改商店资料、审核备注的，改完用同一版本重新提交；需要改代码的，版本还没在任何平台上线时在 `plan.md` 加任务，已经在另一个平台上线时放进下一个 patch 的 `fix.md`。
5. **分阶段放量**：App Store 分阶段发布 / Google Play 分阶段发布；放量期间观察第 4 节的指标。
6. **全量**：把 `scope.md` 和 `doc/README.md` 的状态改为"已发布"，写上日期。

**iOS 和 Android 分开上线时**：`release.md` 按平台分别记录。第一个平台全量后，版本状态就改为"已发布"并做第 3 节的合并；另一个平台上线时只补发布记录。另一个平台如果要先修问题再上，修复放进下一个 patch 版本，可以直接用 patch 版本号首发。

## 3. 发布收尾：合并回基线（必须做）

版本上线后，由 AI 执行合并，用户审核：

1. **需求 → `doc/product/`**：把 `changes.md` 的每个条目按模块合并进对应的基线文件。
   - 写成"现在是什么样"，不写"v2.1 新增""原来是……"。
   - `[删除]` 的从基线删掉；`[取消]` 的不合并。
   - 新模块新建文件，并更新 `product/00-overview.md` 的模块清单。
2. **技术 → `doc/tech/`**：把 `plan.md` 第 3 节的接口、数据库、配置变更合并进 `api.md`、`data-model.md`；有 `tech-design.md` 的合并进 `architecture.md`。
3. **测试 → `doc/testing/`**：值得长期保留的新增用例合并进 `regression.md`（标出冒烟用例）；本版发现的新风险维度补进 `risk-checklist.md`。
4. **`doc/README.md`**：更新线上版本，在版本历史表加一行。
5. **backlog**：没做完、延期的事项回到 `backlog.md`。
6. **冻结版本文件夹**：`scope.md` 状态为"已发布"后，这个文件夹不再修改。
7. **打 tag**：工作台仓库提交文档并打 `{appCode}-vX.Y.Z`（文档归档）；App 仓库打 `vX.Y.Z`；后端有改动的，在后端仓库打 `{appCode}-vX.Y.Z`。由用户执行，或用户同意后由 AI 执行。

合并完成后，AI 给出"基线变更摘要"（每个基线文件改了什么），用户对照 git diff 审核。

## 4. 上线观察

在 `release.md` 记录放量期间和上线后一周的观察：

| 指标 | 基线 | 本版 | 结论 |
|---|---|---|---|
| 崩溃率 | | | |
| 支付成功率 / 订单异常 | | | |
| 关键流程完成率 | | | |
| 接口错误率 | | | |
| 用户反馈 / 商店评论 | | | |

发现问题：
- 线上 bug → 按 `08-线上问题.md` 开 patch。
- 体验问题、新需求 → 写进 `backlog.md`。
- 严重问题 → 暂停放量；需要回滚的按 `release.md` 的回滚预案执行。

## 5. 用户可见的更新说明

写在 `release.md` 的「更新说明」一节，按语言分别写：

- 只写用户能感知的变化，分"新增 / 优化 / 修复"。
- 不暴露任务号、文件名、技术细节。
- 不写本版没有做的东西。
